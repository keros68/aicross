# aicross 用户手册（第一版）

aicross 把本机已装的各家 agent CLI 收进一个窗口：接入资源、看到调用方案、
手动编排；模型提议，用户裁决，控制台执行。本手册对应 0.1.0。

## 安装

Windows 用 `aicross_0.1.0_x64-setup.exe` 或 `aicross_0.1.0_x64_en-US.msi`，
两个装的是同一个程序，装一个就行。运行需要 WebView2，缺失时安装器会补装。
程序数据都在 `~/.aicross/`（资源清单、预设、对话图、任务），卸载不删。
macOS 与 Linux 目前只保证能编译，安装包未做验证。

## 接入资源

接入是申报制：aicross 不扫描本机，只用申报过的资源。

1. 标题栏的插头按钮「接入资源」打开接入页。
2. 按 agent 填 CLI 和可派发的模型（claude / codex / kimi / pi 等）。
3. 探测完就能用。左栏「资源」列出全部探测到的模型，点一下把 `@agent/模型`
   插进输入框；状态、来源路径和最近验证时间在鼠标悬停里看。

左栏的读法：agent 行是各家的标志和版本号；模型行只放模型名和一个状态点
（绿 = 已验证、红 = 验证失败、灰 = 未验证、无点 = 原生）。挂了多个 provider 的
agent（pi）在下面按 provider 分小组，组头写 provider 名和条数；未验证的模型
默认折成一行「未验证 N 个 · 展开」，点开才铺。claude 的 `fable` / `opus` /
`sonnet` / `haiku` 是别名，行内在别名后面浅色显示它对应的真实模型 ID。

验证分两档，不用逐个手点：

- **原生 CLI（claude / codex / kimi 走自家官方端点）**：自家清单说有就是有，
  不验证，行内不带状态点。
- **第三方端点（pi 的各 provider、cc-switch 端点，以及挂了 `ANTHROPIC_BASE_URL`
  的 claude）**：清单里先记「未验证」。第一次派发到它时，控制台自己发一个短请求、
  比对响应体里的模型真身，通过记「已验证」，不通过记「验证失败」并把这次派发按
  失败返回，不自动重试。验这一下防的是静默降级：第三方端点遇到不认识的模型名
  不报错，换个模型照样答。

claude 换到第三方端点（进程环境的 `ANTHROPIC_BASE_URL`，或 `~/.claude/settings.json`
里 `env` 的同名项）时按第三方走。codex 与 kimi 的第三方端点目前还按原生算，
换了端点要在接入页验证。

提前验证或重新验证：接入页的模型详情里点「验证」。

## 总指挥

应用冷启动的首个 tab 和新建总指挥 tab，在默认 agent 已安装且探测完成后直接启动原生 CLI 会话。当前工作区有目录时使用该目录，否则使用已存默认目录。
没有默认、默认 agent 未安装或探测未完成时才显示总指挥启动器；没有可用默认时启动器立即显示，探测期间标「探测中」，可选择本机已安装的
agent、模型和工作区目录后点「启动总指挥」。启动成功后，aicross 会记住这次的
agent、模型和目录；工作区目录行的「在此启动总指挥」会沿用默认 agent 和模型，
只替换目录。

会话上方显示 agent、首次模型和目录，点「更改」回到启动器。显示名统一为
Claude Code、Codex、Kimi Code 和 pi agent；机器 id 仍用于命令和资源记录。

模型来自「接入资源」生成的资源清单，不在启动器中另存一份。Claude Code 显示
别名和已核对到的真实 ID，pi 显示 provider 和 model；选择「不指定」时由 CLI
使用自己的默认模型。工具设置中的额外参数仍会随启动命令传入。

总指挥运行的是 agent CLI 自身，斜杠命令、续聊和权限提示都按原生方式工作。
控制台只传首次启动的模型参数；之后的模型和 thinking 档在会话内按 CLI 自己的
方式调整，例如各家 CLI 的 `/model` 命令。
它不替代对话图：总指挥适合在一个 CLI 会话里持续工作，对话图用于手动编排和
比较多家模型。标题栏「+」菜单可分别打开系统终端、对话图或总指挥。

## 内置预设

预设在右栏「方案与编排」里选，盖在对话图的节点上。预设一律叫「X模式」；
自己保存的预设叫「自定义模式」，多个时显示「自定义模式 · 名称」。

### 基础模式

- **共享模式**：一路执行，能看到上游全部上下文。适合连着几轮推进同一件事。
- **经济模式**：三层。高档位出方案，低档位执行，第三层两路并行：验收（盲、
  只读，看产物给 PASS / NEEDS_FIX）与验证（盲审同一份产物）。派盲审前引擎先
  跑一次验证命令，同批各验证路复用输出 `VALIDATION.txt`。修正轮只看验收那一路；到设置里的「修正轮上限」
  （默认 1）后，未闭合的条目生成一个「遗留」节点挂在验收下，只读、不派发，
  节点面板里可复制清单。贵模型只花在判断上，干活那步换便宜档。
- **盲审模式**：同一份材料同时发给三路，互相看不见，也看不见之前的对话：一路
  验收看产物给 PASS / NEEDS_FIX，两路验证盲审。三路都要在确认派发页选择目标；
  派盲审前引擎先跑一次验证命令，输出随盲节点一起附上，同批各验证路复用。用来核关键产出：不同厂商的失败模式不一样，
  一致才有参考价值。

### 自定义模式

用户保存的预设显示在基础模式之后。只有一个时显示「自定义模式」，多个时显示
「自定义模式 · 名称」。

### 更多模式

更多模式默认折叠，展开后可与基础模式一样选择。

- **擂台模式**：同一材料发给三家执行，共享上下文，结果并排；结果卡上「选定」
  一路，其余候选退出。
- **评审模式**：三个盲验证节点，分别从安全、性能与自定义视角审查同一份材料。
- **蜂群模式**：见下一节。

执行者带上下文是效率，验证者带上下文是污染，所以验收和盲审默认是盲的。
验证角色未指定目标时，除盲审模式与评审模式外，沿用验收角色的默认目标。

## 蜂群模式

一件大活拆成几件互不踩脚的小活，各派一家在自己的 git worktree 里做，做完一件
并一件、并一件跑一次验收。适合能按文件切开的改动；有先后依赖的活别进蜂群。

**怎么盖**：右栏「方案与编排」选「蜂群模式」，盖在根材料上，长出一个拆分节点。
拆分是只读的，用的是「出方案」角色的默认模型，在确认派发页可以改。

**清单长什么样**：拆分那一路跑完，正文里要带一个 json 代码块：

```json
{ "items": [ { "title": "改解析器", "files": ["src/a/**"], "accept": "python -m pytest tests/test_a.py" } ] }
```

`files` 是这件活的文件范围，写 glob；`accept` 是这件的验收命令，可空。
一次最多 4 件，上限在设置里的「蜂群件数上限」，和并发上限在同一处。
解析不出清单时按普通回复展示，结果屏点「按清单生成执行节点」会提示「未解析到清单」。

解析成功后每件生成一个执行节点，写权限是 worktree，节点消息是标题加文件范围加
验收命令。每件只看得到根材料和自己这一条，别人的范围不进它的上下文。件数、范围、
验收命令之后都能在节点面板里改。同一个拆分节点再点一次「按清单生成执行节点」，
已经生成过的件不重复建，超过上限的件不生成。同一张图里再盖一个拆分节点时，
新的件从已有的最大件号往后编，两批件号不撞号。

**派发前的核对**：确认派发页会只读核对一遍清单。没选工作目录时核对发不出去，
提示「未选工作目录，无法核对文件范围」并不放行。核对没回来之前不能确认派发，
提示「正在核对文件范围」；核对不了时说明原因，勾「仍要派发」才放行。两件的 glob
匹配到同一个现存文件算重叠，涉及的路由卡描红，卡片上直接给文件范围编辑框，改到
不重叠或合并成一件才放行，改完自动重核对；项目目录有未提交改动也不放行，合并
要求干净。glob 一个文件都没匹配到只提示，不阻断。

**合并规则**：同一个拆分底下的件全部跑完后，结果屏出「合并」。合并清单按图上的
件算，不按这一次派了哪几件；单件重派或关屏重开之后，冲突件仍在清单里。
按件号顺序来：先在各自
worktree 里 `git add -A && git commit`，再在项目目录 `git cherry-pick`，
成功后跑这件的验收命令（空则用设置里的验证命令）。并进去的每件就是一次 commit，
节点自动标为已采纳，结果写回该节点正文。已并入的件不会再进下一次合并，
合并按钮在没有待并的件时禁用。

蜂群件的结果卡不出「选定」，件与件是分工不是竞争；已并入的件标「已并入」，
不给「重派 / 升级」，也不给「取消采纳」（改动已经在项目目录里）。合并整批的结论按件如实报数
（已并入几件、冲突几件、验收未通过几件）；只有引擎没有这条命令时才说「引擎未接通」。

**出问题怎么办**：cherry-pick 冲突的那件自动 `cherry-pick --abort`，标「冲突待
裁决」，worktree 保留，路径写在结果行里，由用户合并；验收命令非零的那件
`reset --hard` 回上一件，标「验收未通过」，输出折在结果行下面。单件失败不牵连其它
件，后面的件照常继续，也不自动重派。

## `.dispatch/` 是什么

每次派发在项目目录下写一份派发记录：`<项目>/.dispatch/`，一次调用一个 Markdown 文件，
文件名是时间戳加 agent、模型、角色。正文是这次的任务全文和模型原始输出，
头部一段 YAML 记着模型真身、用量、耗时、可见性。

`STATE.md` 记未跑完的那一轮，回到窗口时可以选继续或放弃。
目录建起来时自带一份内容为 `*` 的 `.gitignore`，默认不进版本库。
不想写进项目，在设置里把「派发记录」切到「只写运行目录」，改写到 `~/.aicross/runs/`。

## 密钥怎么处理

aicross 对密钥只做六件事，其余一概不做：

1. 只在本机读，不上传。
2. 只按子进程环境变量传给 CLI，不写任何全局配置。
3. 不回显，界面和日志里都不出现。
4. 不落盘到 aicross 自己的文件里。
5. 不进模型上下文：发出去的任务全文默认过一遍脱敏，见下。
6. 读凭据库之前先提示。aicross 自己不读 `~/.pi/auth.json` 和
   `~/.cc-switch/*.db`。

## 脱敏认什么

脱敏认六类写法：PEM 私钥块、`Authorization: Bearer` 头、
`password` / `passwd` / `pwd` 的赋值、`token` / `api_key` / `secret_key` /
`access_key` 的赋值、AWS 的 `AKIA…` 访问密钥、以及 postgres / mysql /
mongodb 三种连接串里的用户名密码。别的形态认不出来，比如裸写一串
`sk-…`、或 `https://用户:令牌@主机` 这样的地址，都会原样发出去。
规则以 `src/dispatch.rs` 的 `redaction_patterns()` 为准。
派发前的方案页显示这次脱敏了几处；数字为 0 不等于材料干净。

## 首次上手

新装的窗口里，中栏起始视图给出三步：打开目录 → 接入资源 → 选预设，
点哪步跳哪里；有了图或已接入资源之后就不再出现。
三步做完，发第一句话得到根节点，之后 `@` 模型分叉、盖预设编排。

右栏「任务」是一块与派发无关的待办板：状态点一下推进，卡片可拖动排序，
数据存在 `~/.aicross/tasks.json`。文件读不出来时它只读不写，不会覆盖。
