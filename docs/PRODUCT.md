# aicross 产品说明

> 本文只写现行设计。每条规则当时为什么这样定、推翻过什么，见 `docs/history/PRODUCT-0830-0930.md`（08-30 至 09-30 的定案原文）。竞品事实见 `D:\work\agentteam\COMPETITIVE-LANDSCAPE.md`，进度见 `D:\work\agentteam\PROGRESS.md`，任务书与交付流程见 `tasks/README.md`。

## 定位（2026-10-06 用户定）

aicross 是 ai-cross skill 的伴生工具，不是宿主插件：它装在宿主之外，和 CC Switch 同一性质，在外面存好配置、提供执行能力，由宿主里的 skill 读取和调用。对外一句话：把多模型编排变成看得见的配置，把交叉验证的规则交给代码执行。

| 层 | 作用 | 与提示词的关系 |
|---|---|---|
| 配置（`modes.json`） | 用户事先定好的模式与每个位置的人选 | 相当于固化的提示词参数：原本由模型临场判断，改为 skill 读配置照办 |
| 引擎（`aicross dispatch`） | 盲审隔离、真身核对、拦截未发现与验证失败的模型、留痕、回滚 | 不是提示词：写在提示词里模型可能忽略，写在代码里一定执行 |
| 窗口 | 看得见地做选择、事后查看结果 | 配置与查看的界面 |

分工：skill 在宿主里判断何时派发、在对话里征得同意并汇报；aicross 在宿主外保存选择并按代码执行。交付主线仍是 skill，没装 aicross 时 skill 照常可用（退回由模型判断、规则靠提示词约束）；装了 aicross 是可选增强。

## 状态：重新开启，定位为编排配置器（2026-10-06 用户定）

aicross 改做「编排配置器」：窗口里定编排，宿主里执行。参照对象是 CC Switch，它只改宿主读取的配置，用户选完回到原来的宿主工作，不必改变习惯。

重新开启的理由：新手最难的是编排。由宿主里的模型自己判断派给谁（内部编排），新手觉得不可控、看不懂；由用户事先在界面里选定模式和人选（指定编排），skill 照办并在对话里说明，过程可预期。指定编排需要一个看得见的选择界面，脚本给不了。

10-05 冻结的三条理由仍然成立，配置器的范围按它们收窄：

- 独立客户端要用户改变工作习惯：配置器不提供对话窗，也不在窗口里派发，选完即可关闭。
- 价值在规则：规则仍在 skill 与引擎里，配置器只决定「用哪个模式、每个位置派给谁」。
- 多 agent 的面板与状态显示由宿主做：配置器不做实时状态面板。

## 编排配置器

### 一句话

检测本机可用的 agent 与模型，让用户按模式卡片选定编排并存成配置；ai-cross skill 触发时读这份配置照办，执行交给 `aicross dispatch`。

### 页面

1. **资源**：列出检测到的 agent 与模型，每个标就绪状态（可用 / 未安装 / 未登录 / 版本过低）和真身核对结果；可一键冒烟。数据来自现有的 `aicross resources` 与冒烟逻辑。
2. **模式**：内置预设做成卡片，每张卡用一张小图说明阶段顺序、每个位置的角色、谁看得见什么、谁能写文件。每个位置从「资源」页里可用的模型中下拉选人，可设一个备选。选定一张卡为默认模式。
3. **最近的派发**：现有查看器，只看结果、采纳，不在这里派发。

### 编排配置

- 配置写在 `$AICROSS_HOME/modes.json`：默认模式，以及每个模式每个位置的人选（agent、provider、模型、档位、思考强度、一个备选）。派发时位置上有人选就用它；没有再按 `roles.json` 的三个角色补（现有行为）。不加 `--preset` 的派发用默认模式，没设默认模式时仍是经济模式。
- 资源以 aicross 的资源库为准。装了 aicross 的用户，skill 读 `aicross resources` 与 `aicross config show`；没装的用户沿用 skill 的盘点清单。两份不合并。
- 安装包在配置器完成后恢复发布，发布时再定渠道；开发期间不影响 skill 用户。
- 配置是长期默认，切一次一直生效。单次例外在宿主对话里说（如「这次换 Kimi 审」），skill 只对这一次改派，不回写配置。
- 第一版只写 aicross 自己的配置文件，不写宿主的配置（如 Claude Code 的 `agents/*.md`、`settings.json`）。

### skill 怎么用这份配置

1. 触发时先读配置。有配置：按默认模式与人选派发，派发前在对话里用一行说明「按你设定的盲审模式：GLM 执行，Gemini 审」，用户同意后发出。
2. 没有配置：沿用现在的做法，由 skill 按规则判断并提议，同时提示可在配置器里设定。
3. 配置里的模型不可用（未登录、额度用尽、真身核对失败）：按备选顺序改派并在对话里注明；没有备选就停下说明，不自行换人。

### 主 agent（10-06 用户定）

主 agent 是用户直接对话、装着 ai-cross skill 的那个 agent（Claude Code、Codex、Kimi Code、pi 等）。它决定三件事：交叉验证要避开哪家厂商、skill 装在哪里、派发由谁发起。主 agent 没选定，模式的人选就没有意义。

- **配置按主 agent 分开存**：`modes.json` 按主 agent 分组，每个主 agent 各有默认模式与人选。同一个人 Claude Code 与 Codex 都用时，两边的推荐人选本来就不同。资源库是共用的。
- **主 agent 的实际厂商**：按 agent 推定（Claude Code → Anthropic，Codex → OpenAI，Kimi Code → 月之暗面）；接了第三方端点时（如 Claude Code 的 `ANTHROPIC_BASE_URL`、pi 的默认 provider），按端点的厂商算，并在界面上标出推定依据；用户可以手动改。推定不出时记为「未知」，推荐时不把它算作交叉验证的一方。
- **执行时由 skill 告诉引擎主 agent 是谁**：skill 在哪个 agent 里运行它自己知道，派发与读配置都带 `--host <agent>`。引擎不保存「当前主 agent」；窗口里选主 agent 只决定看、改哪一份配置。
- **窗口**：照 CC Switch 左栏的结构，左栏顶部列出本机检测到的 agent（带图标），选一个作为当前主 agent；下方「模式」与「skill」页都按它显示。「资源」与「派发记录」不分主 agent。
- **首次使用的顺序**：探测资源 → 选主 agent → 给它装 skill → 一键推荐 → 按需微调。每一步完成前，后面的页面在顶部用提示条指向这一步。

### skill 安装（10-06 用户定）

三种方式都支持，按人的需要选：**全局**（推荐，默认选中）、**项目**、**由其他软件管理**。

- 安装位置（10-06 按各家官方文档核实）：

  | agent | 全局 | 项目 | 来源 |
  |---|---|---|---|
  | Codex | `~/.agents/skills` | `.agents/skills`（及上级目录、仓库根） | learn.chatgpt.com/docs/build-skills |
  | Kimi Code | `~/.kimi-code/skills`、`~/.agents/skills` | `.kimi-code/skills`、`.agents/skills` | kimi.com/code/docs/…/customization/skills |
  | pi | `~/.pi/agent/skills`、`~/.agents/skills` | `.pi/skills`、`.agents/skills` | pi.dev/docs/latest/skills |
  | Claude Code | `~/.claude/skills` | `.claude/skills` | — |

  因此全局安装写两处：`~/.agents/skills/ai-cross`（Codex、Kimi Code、pi 共用）与 `~/.claude/skills/ai-cross`；项目安装同理写 `.agents/skills/` 与 `.claude/skills/`。只给本机检测到的 agent 写对应位置。
- **我们装的**：从软件内置的 skill 包复制（不含测试），目录里放 `.aicross-install.json` 记录版本、来源与安装时间。软件更新时内置包跟着更新，安装位置显示「可更新」，一键更新；版本以 `SKILL.md` 的 `metadata.version` 为准。
- **其他软件管的**：安装位置是指向别处的链接（如 skillmanager 的 junction 指向 `~/.skills-manager/skills/ai-cross`），或目录里没有我们的标记文件，一律只显示「由其他软件管理 · 版本 x」，不覆盖、不更新、不删除。
- 扫描所有已知位置（含旧位置 `~/.codex/skills`）：同一个 agent 能读到两份 ai-cross 时提示「重复安装」，列出两处路径，由用户决定删哪份。
- 卸载只删我们装的那份。

### 在主 agent 里怎么用（10-06 用户定）

- 配置在窗口里做，使用在主 agent 的对话里：用户说「让别家审一下」或输入斜杠命令，skill 读 `aicross config show --host <主 agent>` 得到默认模式与人选，在对话里确认后经 `aicross dispatch --host <主 agent>` 派发，结果回到对话，详情在窗口「派发记录」。
- 默认调用方式就是调用 ai-cross skill 本身，可带参数（不带参数按默认模式；带模式名只对这一次生效、不回写配置）。各家写法不同（10-06 按官方文档核实）：Claude Code `/ai-cross`；Codex `$ai-cross`（或 `/skills` 选）；pi `/skill:ai-cross`；Kimi Code `/skill:ai-cross`。窗口按当前主 agent 显示它的写法。
- 自定义短命令：用户为某个模式（及可选的固定说明）起一个短名，软件按主 agent 的格式写入：

  | agent | 写入位置 | 用户输入 |
  |---|---|---|
  | Claude Code | `~/.claude/commands/<名>.md`（`$ARGUMENTS` 接参数） | `/<名> …` |
  | Codex | `~/.codex/prompts/<名>.md`（官方已标为将淘汰） | `/prompts:<名> …` |
  | pi | `~/.pi/agent/prompts/<名>.md` | `/<名> …` |
  | Kimi Code | `~/.kimi-code/skills/<名>/SKILL.md`（命令即 skill） | `/skill:<名> …` |

  文件内容是一句固定指令：用 ai-cross skill、按某模式、带 `--host <主 agent>` 处理后面的参数。我们写的文件带标记（frontmatter 里 `aicross-managed: true`），可改、可删；同名但没有标记的不覆盖。定义存在 `modes.json` 对应主 agent 下。

### 一键推荐（10-06 用户定：新人省事，老手不被打扰）

- 每个位置的人选带来源标记：`手动`（用户在窗口或命令行选的）或 `推荐`（一键推荐填的）。
- 「一键推荐」：只填空位置和来源为「推荐」的位置，**不动手动选的人选**。另有「全部按推荐重填」，需要确认，会覆盖手动人选。
- 首次探测完成、所有模式都没配人选时，模式页顶部给一条「一键推荐」的提示条；老手不点就不会发生任何改动。
- 推荐规则复用 skill `inventory.py` 选审查者的规则，不维护在线排名：只选可用或已验证的模型；同一模式里验收 / 验证位置尽量各用不同厂商，且与执行位置不同厂商；订阅制优先、按次计费排最后；出方案用高档，执行用中低档。各家「高档 / 低档」是一张随软件版本发布的小表，和别名表一样随版本更新。
- 推荐过的人选后来变成未发现 / 验证失败时，下次一键推荐自动换人；手动人选只标红提示，不自动换。

## 派发引擎

以下是派发引擎的现行设计，配置器之下的执行部分照此运行。

### 一句话

多厂商 agent 的派发引擎与结果查看器：用户在自己常用的宿主（Claude Code、Codex 等，装 ai-cross skill）里说话，模型提议派发、用户采纳，aicross 负责拉起各家 CLI、隔离盲审、核对真身、留痕，并把各路结果并排交给用户裁决。它把 ai-cross 的规则从"提示词里的纪律"变成"代码保证的默认值"。

## 为什么是这个形态（09-30 定案）

- **尺子**：aicross 做成什么样算对，看它像不像开发它时用的工作方式——一个长期对话窗，只跟一个协调者说话，协调者不写代码，只规划、派活、把结果拿回来给用户检查，关键产出由另一家盲审。让这种工作方式更容易复刻，就值得做；只让界面更热闹，就不值得。
- **宿主已经是好对话窗**：在 Coffee CLI 的终端工作区上叠控制台、对话图、编排面板之后，界面层数过多，用户自己用着晕，不如直接用 skill。
- **多 agent 的可见界面可以很小**：对话里一行状态，点开看详情（CodePilot 的做法，见竞品文件 09-30 节）。
- **代码只保证提示词保证不了的部分**：盲审隔离、模型真身核对、留痕与对账、结果并排裁决。aicross 只做这部分。

## 机制

1. **说话的地方是宿主**。用户照常在 Claude Code、Codex、Kimi 等里工作，ai-cross skill 装在宿主里。aicross 不提供对话窗。
2. **G1 在对话里**。skill 给出一行建议（模式、几路、各派给谁；有编排配置时按配置），用户在对话里同意才发。永不自动执行：漏判只是少一次核对，误判要花额度、可能改文件。
3. **引擎是命令行**。`aicross dispatch` 在不开窗口时跑完整条流水线：拉起各家 CLI、盲目录与隔离、只读护栏、真身核对、留痕、验证门、修正轮、红绿核对、额度切备选、崩溃对账。`aicross status` 给每一路一行状态，skill 在对话里逐路报告。
4. **收尾回到对话**。全部结束后 skill 在对话里给汇总：共同结论、分歧、各自独有发现，附查看器入口。
5. **G3 在查看器**。一次 run 一页：各路并排、diff、验证输出、真身与用量，动作只有采纳 / 重派 / 放弃。
6. **资源接入是命令**。探测、冒烟、就绪状态由 `aicross resources` 输出。

对话图（节点 = 一轮，分叉 = 派发，扇入只有验收）是引擎的内部表示与留痕结构，不是用户要操作的界面。

## 规则

### 每次派发一张图

每次 `aicross dispatch` 新建一张图，派发之间不共享上下文（10-01 用户定，TASK-38）。上下文在宿主里：对上一次结果的追问、返工，由 skill 把必要的前情写进这次的任务文本。run 摘要的遗留、查看器的标题与遗留因此只属于本次派发。

### 可见性跟角色走

- **执行者**默认共享上下文。
- **验证者**默认盲：原始材料放进空目录，注入 `AI_CROSS_PEER=1`，只读白名单，材料走 stdin，关掉宿主自己的用户级指令加载。
- **盲的边界**（09-01 实测）：空目录只挡项目级文件；`claude -p` 加 `--restricted` 才不注入用户级 `~/.claude/CLAUDE.md`；`CLAUDE_CONFIG_DIR` 指向空目录会连凭据一起隔离掉，不能用。测不出等价开关的通道标「隔离：部分」，不按盲算。
- 被派方互不可见，拓扑是星形；同一目录同时只有一个写者。
- 共享对话类模式在结果上标「此模式下各方结论不独立」，不作验证用。

### 三个引擎、两个开关

模式可以多，机制只有三种。新模式 = 给某个引擎换一套预设。

| 引擎 | 机制 | 写盘 |
|---|---|---|
| **扇出比对** | 同一份输入 → N 个隔离实例 → 收回并排 | 只读 |
| **流水线** | 阶段串行，上下文往前传；一个阶段内可并行 | 单写者 |
| **分工合并** | 拆任务 → 各领一块（各自 worktree）→ 合并 | 多写者 |

每个节点两个开关：**可见性**（共享 / 盲 / 只收指定上游）、**写权限**（只读 / 单写者 / 自己的 worktree）。

### 模式

| 模式 | 引擎 | 用途 | 状态 |
|---|---|---|---|
| **经济模式** | 流水线 | 出方案 → 执行 → 验收，验收默认换厂商 | 已有 |
| **盲审模式** | 扇出比对 | 同材料、隔离、并排、独有发现单列 | 已有 |
| **共享模式** | 共享对话 | 一个 thread 大家都看得见；只读 | 已有 |
| 擂台 / 评审团 / 仲裁 / 前提抽查 / 主备熔断 / 顾问 | 扇出比对或流水线 | 见历史文件「模式清单」 | 预设已有；各自的结果页动作待查看器承接 |
| 蜂群 | 分工合并 | 任务明确的并行开发 | 窗口版已有，无窗口版另起一期 |
| 红蓝对抗 / 群聊 | 共享对话 | 要的就是互相影响 | 不排期 |

界面与 skill 里一律称「X 模式」。命令行别名：`shared` / `economy` / `blind`。共享模式那一路按设计只读，要改文件派经济模式。

### 经济模式

五轮基准的结论：档位几乎不影响正确率；便宜模型翻车只有两种情况——深任务关了 thinking、让模型亲自算而不是写代码。预设把这两条写死：

1. 三个角色一次定（出方案 / 执行 / 验收），每个角色选厂商 + 档位 + thinking，之后复用。
2. 执行者遇链式任务自动开 thinking；数值任务提示词强制「写代码并运行」；单步小任务不外派；同类小任务合并；harness 通道收窄 `--tools`。
3. 每阶段只展示用了哪些模型、多少 token、多长时间。
4. 验收默认换厂商；用户改回同厂商时标「复核，非独立验证」。

边界如实说：每次 harness 调用约 12k 的系统提示底座砍不掉。对外按「贵模型用在该用的地方」说，不按「省钱」说。

### 验收与盲审的材料

- 验收节点收「用户原话 + 上游产物」，不收上游的推理与方案；盲审节点只收原始材料。并行节点之间互不可见。
- 执行产物：执行节点前后快照 → `Reply.artifacts { diff, changed_files, worktree?, stdout_summary }`，外发前六类脱敏。盲验收目录放 `REQUEST.md` + `diff.patch` + `changed/`，diff 小于 30KB 时同时内联。
- 只读任务没有 diff 时，执行者最终回复作为 `ANSWER.md`，另附项目只读副本 `project/`（只含版本库跟踪的文件，不含留痕、其他审查者产物与密钥类文件）。「盲」指看不到执行者的过程与推理，不指看不到项目。
- 审查材料附验证命令的输出；审查提示词固定关注「契约有没有变」「新增测试能不能红」。

### 修正轮与验证

- 修正轮上限默认 1；到上限未闭合的问题生成「遗留」节点（只读清单），不再派模型。
- 验收与盲审同阶段并行，互不等待。
- 验证命令失败的修正轮 ≤ 3 轮；验证未过时验收节点标「已跳过」。
- 红绿核对自动做、不阻断：修正轮交回的测试，回退到派发前快照跑一次（期望失败）、恢复再跑（期望通过），结果标「测试已钉住 / 测试未钉住」；「未钉住」按未修好计入修正轮上限。

### 额度与备选

- 429 / 403 / session limit / resets at 这类响应识别为额度用尽，节点状态 `quota_exhausted`，不算失败。
- 有备选按用户排的顺序切，结果注明「主 X 额度用尽，已切备 Y」；全部用尽把恢复时间写进节点。skill 读到 `quota_exhausted` 就换厂商派，不等配额。

### 重派与崩溃恢复

原则：**diff 即事务，采纳即提交**。效果收在 worktree 或文件改动里，回滚 = 丢弃，提交只发生在 G3 采纳。

1. 单写者节点重派前，先把上次改过的文件恢复到派发前快照（`.dispatch/<run>/<node>.before/`），删掉新建文件；worktree 节点每次从 HEAD 新建。项目目录有未提交改动时提示「worktree 看不到未提交改动」。
2. 崩溃后继续先对账：有 `status: ok` 留痕 → 直接收回；有失败留痕 → 重跑；没有留痕 → 标「待核对」交用户，单写者节点不自动重跑。无窗口引擎的后台进程死了，run 标失败「引擎进程已退出」，不自动重跑。
3. 外部副作用不可回滚：执行者提示词固定禁止 push、发布、装包、调付费接口；codex 走 `-s workspace-write`（默认禁网），claude 走 `--tools` 白名单，kimi 一次性调用只靠提示词。

### 资源接入与真身核对

- **原生**（claude / codex / kimi 的自家模型，且没走第三方端点）：读清单即可用，只探 agent 在不在、登录了没。claude 挂了 `ANTHROPIC_BASE_URL` 按第三方算。
- **第三方**（pi 的各 provider、cc-switch 端点）：第一次派发前引擎先冒烟一次，比对响应体的 `model`，结果记为未验证 / 已验证 / 验证失败；验证失败的派发直接返回失败，不自动重试。
- **别名的真身**：claude 的 `fable` / `opus` / `sonnet` / `haiku` 等别名记 `resolved_id`，第三方端点以实测值覆盖，`resolved_source` 记是算的（`alias-table`）还是量的（`identity`）。
- **通道**：claude / codex / kimi 三个 CLI 只承接各自的官方订阅；其余模型一律经 pi（固定开销最小、`--no-context-files` 可做完整隔离、密钥归 `pi auth` 管）。盲审、仲裁、前提抽查默认走 pi `--no-tools --no-context-files`，真身看事件里的 `responseModel`。cc-switch 只作发现提示。
- pi 只列已登录的 provider：先跑 `pi auth check --provider <p> --json --no-refresh`，不读凭据。
- 接入是申报制：不盲扫本机，用量痕迹只做发现提示，纳入须用户确认。

| agent | 存在检测 | 模型清单 |
|---|---|---|
| Claude Code | `claude --version` | 官方型号，无本地清单 |
| Codex | `codex --version` | `~/.codex/models_cache.json` |

### 蜂群（窗口版已有，无窗口版另起一期）

大任务先由「出方案」角色拆成至多 4 件互不踩脚的小活（清单带标题、文件范围 glob、验收命令），文件范围重叠的必须改到不重叠或合并，有先后依赖的不进蜂群。每件各派一家在自己的 worktree 做，完成后在各自 worktree 提交，项目目录（必须干净）按清单顺序 `cherry-pick`，每并一件跑一次验证：冲突 → 中止并留 worktree、标「冲突待裁决」；验证红 → 退回上一件、标「测试红」。单件失败不停整批。冲突不自动解，也不派模型解。无窗口版要把「清单确认」这道 G1 放进宿主对话。

## 与 ai-cross skill 的关系

- skill 是用户面：判断何时建议派发、在对话里报状态与汇总。aicross 是执行面。
- 契约是命令与文件：命令行 `aicross dispatch / status / adopt / cancel`（协议全文 `docs/CONSOLE-CHANNEL.md`）；留痕 `.dispatch/*.md`（`aicross-dispatch/1`）；run 摘要 `~/.aicross/runs/`；派发设置 `~/.aicross/dispatch-settings.json`。
- aicross 不可用（退出码 3）时，skill 回退到直接调各家 CLI。

## 不做

- 不做对话窗、终端托管、编辑器、文件浏览器。
- 不做通用 agent 框架，不定义新协议。
- 不复用第三方对订阅 OAuth 的封装，只拉起官方 CLI 进程。
- 不做自由连线的节点编辑器。
- 不做成本核算（美元、额度百分比）。
- 不管理供应商与密钥（交给 CC Switch、pi 等，只读取）；不做用量统计。窗口页面限于资源、模式、派发记录与 skill 安装。
- 安装包体积控制在几 MB：用系统 WebView，不打包浏览器；新增依赖要说明体积影响（10-06 release 版 `aicross.exe` 4.7 MB，含前端）。
- 不做云端常驻、多用户、手机端。
