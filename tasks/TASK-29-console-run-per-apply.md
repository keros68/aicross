## 86. 第二次应用模式沿用上一次的对话图，阶段号与修正轮上限都累计

实测：同一控制台里先跑一次经济模式（出方案 → 执行 → 验收/验证 → 修正执行 → 验收/验证，共 5 阶段），再对新消息应用经济模式：
- 新运行的系统提示与详情页从「第 7 阶段」开始（用户看来应是第 1 阶段）；
- 验收判 NEEDS_FIX 后**一轮修正都没跑**，直接收尾「未通过（验收要求修正，已到上限）」，共 4 路。

原因方向（请先核实再动手）：`dispatchConsolePreset` 用 `snapshot.existingGraph` 续写同一张图；阶段号取 `graphStage`（图上深度），修正轮计数（`graph/dispatch.ts` 约 810–830 行 `fixRoundLimit` 相关）按整张图统计 NEEDS_FIX 或修正节点。

要求：
1. 每次应用模式，**展示给用户的阶段号**从 1 起（系统提示、详情页分组、收尾结论里的「第 N 轮」）。引擎请求里的 `stage` 若只是排序用、改了有风险，可以只在展示层换算，报告里写清选择。
2. **修正轮上限按本次运行计**：只统计本次应用新建的节点。上一次运行留下的 NEEDS_FIX / 修正节点不占本次额度。
3. 续写同一张图带来的上下文延续（上一轮对话作为材料）保持不变——不要为了修这条改成每次新建空图，除非核实续写本身就是缺陷并在报告里说明证据。
4. 旧画布（`DispatchOverlay`）的行为不变；若必须改 `graph/dispatch.ts` 的共享函数，用参数区分（例如传入本次节点集合），旧调用点行为用测试钉住。
