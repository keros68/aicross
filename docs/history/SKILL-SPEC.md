## 目标

搭一套个人 AI 工作流：按任务难度和类型分层调度模型，覆盖 **AI coding** 和 **学术科研** 两个场景（一起搭，共享一套调度骨架）。优先级：**质量 > 省钱 > 省心**。

## 首版范围（已锁定）

| 决策点 | 结论 |
|---|---|
| 模型接入 | 首版只用 **Claude（订阅）+ Codex（订阅）** 双模型；Gemini/智谱/Qoder/其他 API 留到第二阶段 |

## 核心流程

```
需求梳理（轻量追问）
  → 主 agent 按规则表路由（简单→便宜快模型；复杂→强模型）
  → 执行
      coding：单个或并行 worker 实现 → 对方模型 review → 修正 → 再 review（≤3 轮）
      科研分析：≥2 agent 独立执行 → 交叉比对 → 一致则过 / 不一致报人工
  → 汇总报告（含证据、分歧、未验证项）
```

## 修订 v1.2（2026-07-08）

**通道架构扩展 —— coding plan 端点方案反转采用（推翻 v1.1「不采用」）：**
- 新增「外部-coding plan」通道：载体是 `claude -p` + **按进程环境变量覆写** `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN`，接 GLM Coding Plan、Kimi Code 等 Anthropic 兼容端点。
- v1.1 担心的「OAuth 与 BASE_URL 互斥、共享 ~/.claude 踩踏」已被**进程隔离**解决并实测证伪：环境变量按进程生效，子进程覆写不影响宿主会话登录/settings.json/进程环境。**实测（claude 2.1.204，2026-07-08）**：CLI 明确以注入 auth 源优先于 claude.ai 登录，被重定向子进程与官方子进程可并发共存互不干扰。
- **铁律**：覆写只按子进程传，绝不写全局 settings.json（写全局才是 v1.1 担心的踩踏根因，常见于第三方「一键助手」）。
- 关键端点：GLM `open.bigmodel.cn/api/anthropic`（变量名 AUTH_TOKEN；模型 GLM-4.7 / glm-5.2[1m]）；Kimi `api.kimi.com/coding/`（模型 kimi-for-coding）。
- aichat 定位收窄为**纯按量 API 兜底**（DeepSeek/OpenRouter 直连），不再兜 coding plan。

**能力探测改为申报制（推翻盲扫）：**
- 用户勾选自己有哪些订阅/API，只验证勾选项，不盲扫全机。信任级别=用户申报。
- 派发门槛按**厂商/档位**而非源数：分层省钱任一源 ≥2 档即可；交叉验证需 ≥2 个不同厂商（错误相关性更低；跨厂商降低相关、不消除）；全力用可用模型尽量都上。源只用于计费提示与独立性判断。

**壳 ≠ 模型（关键认知）：**
- zcode/ZCode、Qoder 桌面、Hermes、OpenClaw、WorkBuddy 是 harness/壳，不是可派发模型。派发目标永远是模型，经三种方式触达：①官方 CLI ②Anthropic/OpenAI 兼容端点 ③按量 API。
- 路由壳给不了新的触达能力（它自己也靠上述方式触达模型），只多一层折损。定位：可作宿主、或一条可选外部通道（如 `hermes chat -q`），非必经之路。

**cc-switch 结合 —— 只读预填源，不重造：**
- cc-switch（44k star，多模型用户主流配置工具）的 `~/.cc-switch/cc-switch.db`（SQLite）存用户手动添加的各 CLI 供应商。作为盘点的**可选预填源**（免用户重输），只读。
- **实测（2026-07-08）**：provider 列表总能读到；端点在 `provider_endpoints` 表可靠读到；**有保存 key 的 provider，token 明文存于 `settings_config.env.ANTHROPIC_AUTH_TOKEN`**（讯飞证实，cc-switch 不加密第三方 key）。空/陈旧条目无 token（初测 GLM 条目恰为久未使用、key 未保存，非结构性读不到）。故定位可选、读不到 key 回退用户补。
- **铁律**：只读、绝不改其 db、绝不用其「切换」机制（它靠写全局 settings.json 切换、一次只激活一个，正是要避开的全局污染）。我们的差异价值：它存多个只跑一个，我们用按进程 env 让多个并发跑。

**形态决策 —— 做 skill 不做外挂：**
- 系统分两层：配置层（静态 CRUD，app 擅长，cc-switch 已解决）+ 决策层（任务级路由/互验，需任务语义与实时中间结果，只存在于 agent 内）。
- 决策层必须在 agent 内 → skill（或 in-agent）是唯一合适形态；符合「跑在各 agent 里、零安装分发、主 agent 自主 fan-out」的硬约束。做成外挂要么重造 cc-switch、要么被迫内置 agent 变成 OpenClaw/Hermes 式重型框架（已否）。
- **伴生 CLI 作为未来可选项**：若将来需要代码级强制的密钥安全，可加极薄伴生 CLI（自管配置 + 稳定 JSON 接口 + 白名单出网），skill 靠「命令模板+模型参数」抽象随时能接入，其余逻辑不改。

**密钥安全 —— 本地 ≠ 杜绝：**
- 本地编排消除「我们的服务器/中转」这一泄露口，但不能「杜绝」泄露。残余通道：①key 必然到自己 provider（预期）②**头号风险：key 溜进云端 agent 的上下文/transcript**（执行 skill 的 agent 本身是云端模型，含 key 的命令回显或配置读入即离开本机）③本地明文静态存储。
- 安全 = 本地编排 + **处理纪律**（六条铁律：本地只读/绝不外传/不回显打码/不落盘到自身文件/不进模型上下文/读凭据库先告知），纪律针对的正是头号风险。
- 硬堵头号风险的 path = 伴生 CLI 让 key 全程不进 agent 视野。

**结构重构（减负）：**
- SKILL.md 只留决策核心（4.6KB，触发时注入）；接入向导 `references/setup.md`、命令模板 `references/channels.md` 按需 Read（渐进式披露），日常派发不加载。

## 修订 v1.4（2026-07-08 夜，三轮基准后 —— 核心决策模型重心转移）

### 决策模型改写：档位从「能力维度」降级为「成本旋钮」

三轮基准（含 4 个自造硬任务：跨午夜时段语言 / 自造校验和含负数取模陷阱 / 51 步精确递推 / 规格歧义题）的一致结论：**档位几乎不影响正确率**。最便宜档在全部硬任务上与最贵档持平；最贵档只多烧约 2× 推理 token。

**路由改为三步走**（见 SKILL.md）：
1. **这个任务要模型亲自算吗？**（最关键）
2. **选通道**（看 manifest 的质量备注，不看档位）
3. **选档位 = 选成本，默认最低**，验证失败再按升级阶梯往上

### 升级阶梯重排（按实测收益，不按传统 cascade）

| 顺序 | 动作 | 实测收益 | 代价 |
|---|---|---|---|
| ① | 查输入是否送达 | 曾把整套基准误判为 0% | 零 |
| ② | 改任务框架：让模型写代码，别让它心算 | StepFun 33% → 100% | 零 |
| ③ | 换厂商 | 修复系统性缺陷（同厂商升档无效） | 一次重派 |
| ④ | 咨询顾问一次（advisor） | 未被检验（天花板效应） | 2.1× input、2.2× 耗时 |
| ⑤ | 升推理强度 / 升档位 | **零准确率增益** | 约 2× 推理 token |

**传统 cascade 把 ⑤ 当第一手；我们的数据说它是最后一手。**

### 三条新的实测结论

1. **「模型亲自算」vs「模型写代码让机器算」是真正的分水岭。**
   同一个 StepFun：写校验和算法的代码 100%，亲自迭代 51 步只有 33%，肉眼数 assert 也只有 33%，统计任务方法标注错 + 两处算术错。`step-mid` 同为 33% —— **升档救不了**。
   **更严的复测**：自算不可靠是**随机的**，不是通道开关。StepFun 复测 5 次错 1 次；"全对"的 GLM 在独立探针里第一次就错。
   → **铁律（不分通道）：精确数值一律让模型写代码由机器执行；做不到则编排者独立核验。绝不采信任何模型的自算——包括最贵的那个。**

2. **固定开销是「壳」的，不是「模型」的。**
   同一个 haiku、同一个空任务：内部 subagent **3,963** token；外部 `claude -p --model haiku` **30,230** token。**7.6×**。
   → **有内部通道先用内部**（Claude Code 的 scout/worker/heavy 分层几乎免费，workflow/ultracode 式扇出经济上完全成立）。**跨 CLI 外派的唯一正当理由是换厂商做交叉验证。**

3. **advisor 模式的经济学在 CLI 架构下反转。**
   Anthropic 称 Sonnet+Opus顾问 成本反降 11.9%；我们实测 **input 2.1×、耗时 2.2×、正确率零增益**。原因：原生 advisor 是 API in-request 工具**不重发上下文**，跨 CLI 咨询每次付一次完整冷启动足迹。
   **天花板效应**：执行者本就 100% 且零 thrash，顾问无错可纠——故该收益**既未复现也未证伪**。
   → advisor 只挂在升级阶梯第 ④ 级，**绝不预防性开启**。

### 方法学（固化为纪律）

- **第 0 条：先证明尺子是准的。** verifier 必须过正/负样本自检才能用于判定。本项目自检抓到：把 CLI 横幅当代码 `exec()`、负样本靠 `range(step=0)` 副作用蒙混、`items.sort()` 改入参因入参本就有序而检测不出。
  - **尺子之外，题也要自检。** `tasks_depth.py` 的参考实现里加断言，当场逼停了三道坏题：约束满足题有 2 个解（不唯一）、状态跟踪题中间态出现"−2 个红球"（考的是模型肯不肯输出荒谬答案，不是推理）、多跳算术题的答案恰好是题面数字的一半（可蒙对）。**GT 必须由参考实现算出，不许手写；深题的答案字串不得出现在题面里（防泄漏检查）。**
- **判定模型失败前，先 dump 出它实际收到的输入。**
- **判定模型答错前，先确认它说完了没有。** `content` 为空即失败，按 `finish_reason` 归因（`truncated`/`empty`）；**绝不回退去读 `reasoning_content`**——思考是草稿不是答案。`completion == max_tokens` 是撞顶指纹，该次调用无效。
- **任何 thinking on/off 的比较都必须报告截断率。** 推理 token 与答案 token 共享输出预算；截断率不为 0 的格子，其正确率不得用于比较。
- **一个解释越符合直觉，越要先去查它赖以成立的那个数字。**（overthinking 是个好故事，好到没人去看 512 是不是恰好等于 `max_tokens`。）
- 任何 token/成本测量必须**区分冷/热并报告 `cache_read`**；单次测量不得用于下结论。
- 只用结构化用量（`codex exec --json` 的 `turn.completed.usage`；`claude -p --output-format json` 的 `usage`），**绝不用 codex 打印的 `tokens used`**。

## 修订 v1.5（2026-07-10，外部评审触发 —— 推理轴改写 + 核心论证重定位）

**触发**：把 v1.4 的结论拿给 Claude 网页版与 GPT 网页版评审，两者独立指出同一个问题：
「有唯一答案 ⇒ 不需要推理」这条轴画错了。数学证明、代码调试、约束求解全都有唯一可验证答案，
却正是推理模型收益最大的地方（RLVR 这条训练路线本身就依赖 verifiable reward）。
复查时探针撞出真因，连带撤回了一条已发布的结论（见撤回表 #8）。

### 一、轴改写：从「有无标准答案」到「搜索深度」

新基准（`bench/RESULTS-DEPTH-20260710.md`，5 模型 × 10 任务 × 2 臂 × n=5 = 500 次调用，裸 API）。
两组任务**都有唯一的、程序可验证的答案**，唯一区别是答案在不在输入里：

| 深度 | thinking | 正确率 | completion 中位 | 净效应 |
|---|---|---|---|---|
| shallow（答案已在输入里） | off | 99% | 4 | — |
| shallow | on | 100% | 158 | **+1 pp，40× token** |
| deep（答案须多步推导出来） | off | **26%** | 5 | — |
| deep | on | **91%** | 827 | **+65 pp，165× token** |

**5/5 模型在深端均为正增益（+30 ~ +100pp），0/5 在浅端有实质增益。**

→ **旧判据作废**：~~「只在没有机器可验证的正确答案时调高推理」~~
→ **新判据**：**按从输入到答案需要走多少层相互依赖的变换来调。**
- 答案能直接定位、复制、按固定规则转换 → 关思考 / 最低档
- 需要 ≥2 步相互依赖的推导（前一步错则全错）→ 中档
- 需要比较多个假设、处理冲突约束、搜索多条路径 → 高档

**深度轴是连续的**：`extract-amounts` 因为多了"去重+排序"一步就有 +8pp；`multihop` 即便开思考也只有 67%。

### 二、关思考的失败形态：自信的假数字（新增铁律）

deep × off 的 74 次失败中，**失败模式 100% 是 `wrong`，零拒答、零空输出**。
模型用 1–9 个 token、以完美格式给出错的数（`d-recur-11` 关思考 25/25 全错，输出 `988`/`916`/`470`，正确答案 256）。

→ **铁律：「默认关思考」这条省钱建议，必须与「先判断任务深度」绑定，不得单独成立。**
浅任务上它省 40–165× token；深任务上它给你一批**格式完美、无警告信号、可以直接入库的假数字**。
这与既有铁律「绝不采信任何模型的自算」是同一件事的两面。

### 三、thinking 是与档位**正交**的第三个旋钮（补齐规格缺口）

v1.4 的路由表只输出「档位（低/中/高）」，无法表达 thinking。但二者正交：
**「Haiku 开思考」和「Opus 关思考」都是合法且有用的格子。**

- **档位** = 选哪个模型（成本旋钮，实测几乎不影响正确率）
- **thinking** = 让所选模型走多深的搜索（**能力旋钮，在深任务上是决定性的**）

路由表须同时输出两者。**不要用升档去替代开思考**——同厂商升档救不了深度不足（v1.4 已证：haiku→opus 在"亲自算"任务上有增益，但那本质是深度差异）。

### 四、核心论证重定位：交叉验证 = 给没有 verifier 的任务外接一个 verifier

两位评审独立收敛到同一条：**可验证任务的最优策略不是延长单条推理链，而是「短推理出候选 + 外部验证 + 修正」。**
自我反思只是同一个分布里的又一次采样，不引入独立证据。

这正是 `ai-cross` 存在的理由，且比"省的是额度不是美元"硬得多：

- 跨厂商交叉验证 = **给一个本来没有 verifier 的任务外接一个错误相关性更低的 verifier**。09-14 收窄：Correlated Errors（2506.07962）与 Beyond Self-Checking（ICLR 2026 workshop）实测跨家族相关 ρ≈0.54、同家族 0.77，越强的模型错误越相关——跨厂商只是降低相关，不消除；能跑的测试、GT、原始材料核对仍是第一验证手段（见 `COMPETITIVE-LANDSCAPE.md` 2026-09-14 节）。
- 这解释了为什么 ultracode / workflows 那类**同厂商多 agent 扇出抓不出 Claude 自身的系统性盲区**——同一个分布里采样再多次，也不是独立证据。这是 ai-cross 唯一不可被宿主内建能力替代的价值。
- **推论**：边际预算优先给独立验证，而不是给更长的推理链。有计算器就用计算器（既有铁律「精确数值一律让模型写代码」正是此理），有第二个厂商就派给第二个厂商。

**同时收窄适用边界（诚实声明）**：本轮 deep 任务全是符号/算术型推导，**开放式权衡任务（架构取舍、方法学审查）没有测，也无法用本方法测**——它们没有程序可验证的答案。故：
> 对开放式任务，长推理**可能**多想到一个约束，也**可能**只是产出一段更长、更自洽的 rationalization，而没有反馈回路能区分二者。
> **这类任务上，把预算花在换厂商拿独立第二意见，比花在让同一个模型多想 2000 token 上更可辩护。**
> 输出当 checklist 用，不当结论用。（`geochem-mechanism-reviewer` 里"只批判、不补漏"的角色边界，本质就是在手工补一个缺失的 verifier。）

### 六（2026-07-11，用户提出）：验证的框架隔离 —— 模型独立 ≠ 验证独立

用户观察：项目内交叉验证共享前期积累，而他把背景值论文拿去**无痕模式问零上下文的网页版模型**，得到了项目内从未出现的结果——项目会不会被自己的记忆锁死越走越歪？

判定：**会，且本项目已被咬过**（512 假象在项目内活了一整天，破局的正是零上下文外部模型攻击前提）。但锁死位置要说准：被派模型看不到项目记忆（子任务自包含），**传染通道是编排者写 prompt 时的框架选择**——问题表述、材料挑选、把旧结论当已知事实。与蒸馏问题同构：蒸馏是训练层同源化，共享出题框架是**推理时同源化**。

已写进 SKILL（「验证的框架隔离」节）：
- **盲验原则**：验证 prompt 只给原始材料+中性问题；"请验证 X"是确认偏误邀请函；已固化结论（含铁律）不得作为背景事实进验证 prompt。
- **隔离分级**：同会话复查 < 新实例+编排者框架（旧默认）< **盲验新实例（交叉验证新默认）** < **零上下文人肉转发（用户换表述问全新会话——项目核心前提定期走这级，它是唯一能抓"全项目一起想歪"的层级）**。
- 概念区分：**执行者带记忆是效率，验证者带记忆是污染**——传承与隔离按角色拆开，不是二选一。

### 五、评审本身演示了它警告的东西

核实两位评审引用的四篇 overthinking 文献（arXiv:2412.21187 / 2503.01141 / 2504.05419 / 2504.13367）：

**明确不采纳**：把 thinking 的开关判据交给"用户明说要深推理"（其 guidance 原文）。这正是我方实测的塌方点——深任务关思考时 72 次失败全是 wrong、零拒答，用户根本不知道该开口。我方判据保持"有没有链式依赖"+3 连发探针，**这是相对一个大厂官方 selector 的可指名差异，articles 可用**。另：其"场景维度"（Batch API 五折 / 上下文缓存 / 流式）不进路由表，理由见下方实测。

**实测：`claude -p` 固定足迹随 `--tools` 分档（claude 2.1.232 + haiku，2026-08-14，n=1/配置）**

| 配置 | 总 input | 相对默认 |
|---|---|---|
| `--tools ""` | 12,239 | −61% |
| `--tools Read,Grep,Glob` | 14,238 | −54% |
| 不传 `--tools` | 31,275 | 基准 |

三条结论：
- **一直被引用的"`claude -p` ≈30k"是"不传 `--tools`"的值**，而我方所有模板都传 `--tools`。数字没错，但被放在推荐收窄工具的语境里引用，**掩盖了自家护栏的省额度效果**。
- **修正一处操作性表述**：原文"固定开销里，工具定义是能力、系统提示才是可省的开销"——实测反过来，可裁的正是用不上的工具定义（19k，占默认足迹 61%），砍不掉的是 ~12k 系统提示底座。改写为"需要的工具别省，用不上的一律关；手写模板漏 `--tools` = 白付 2.5 倍"。**对订阅用户，这是订阅内能拿到的最大一笔省，且不用改走按量裸 API。**
- **负结果**：`--exclude-dynamic-system-prompt-sections` 只省 1.3%（12,229→12,071），是为跨用户共享缓存设计的，不进路由表。冷/热双峰同轮复现（重跑 `cache_read` 全额命中 12,229、fresh input 仅 10）。

**顺带记录**：`claude 2.1.232` 有 `--fallback-model <a,b>`（主模型过载自动按序换）——可作熔断的 CLI 层兜底，但它换模型不换厂商，不构成独立源。

**待决（未做）**：其"场景维度"里的 Batch API 五折 / 上下文缓存开关，本机三个 CLI（claude/codex/kimi）`--help` 全无对应参数，只有裸 API 层才有；而裸 API 对订阅用户是掏钱通道。**结论倾向：这一格对订阅用户价值有限，暂不进路由表**，等有按量用户场景再评估。

- `run`（让别家干活）：把任务文本原样发给默认执行者或点名的条目，可附参考材料。执行者没有工具，交回文字，落盘与跑测试由宿主做。不加 claude 的 `--restricted` 与 pi 的 `--no-context-files`，留痕记 `role: 执行`、`visibility: 共享`。
- `smoke`：给条目里每个档位的模型各发一句话，有一个档位不可用整条标失败并写明是哪个模型。
- 三者共同：不带 `--go` 只出方案，什么都不发送；方案输出就是路由决策行加外发说明。当前会话带 `AI_CROSS_PEER=1` 时拒绝执行。脚本不读密钥，cc-switch 条目交给 `cc_switch.py exec`。

`inventory.py` 抽出 `choose_reviewers` 与 `mark_smoke` 供派发脚本复用，`pick` 的输出不变。

**各通道的实际写法**（依据同日真机抓到的输出形状）：claude `-p --tools "" --restricted --output-format json`；codex `exec … -s read-only --json -`，回答取全部非空 `agent_message`（正文在倒数第二条，最后一条只是收尾的一句话）；pi `-p --no-tools --no-extensions --mode json --no-context-files --thinking …`，只认 `text` 块；agy 走 stdin 的 NDJSON，`response` 为空判失败；kimi 走命令行参数，材料超过约 30KB 跳过；cc-switch 经桥、隔离记为部分。

## 修订 v1.19（2026-10-25，盘点后发现新模型，版本 1.22.0）
