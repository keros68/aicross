## 一句话

多厂商 agent 的派发引擎与结果查看器：用户在自己常用的宿主（Claude Code、Codex 等，装 ai-cross skill）里说话，模型提议派发、用户采纳，aicross 负责拉起各家 CLI、隔离盲审、核对真身、留痕，并把各路结果并排交给用户裁决。它把 ai-cross 的规则从"提示词里的纪律"变成"代码保证的默认值"。

## 解决什么

| 痛点 | 现状 | 本产品 |
|---|---|---|
| 性价比：想"强模型出方案、便宜模型执行、强模型验收" | 在 Claude Code / Codex 里手工配子 agent 上手难；自动挡（ultra 类）既不省也不快 | 一次定角色，之后每个任务复用；经济预设内置拧对旋钮的规则（见「经济模式」） |
| 准确度 | 同厂商复查失败模式相关 | 验收默认换厂商；盲审是一等公民 |
| 可控 | 模型既提议又执行，用户只能看 | 派发前、收结果时两道闸门，不点不发 |
| 上手 | 写 agents/*.md、记 CLI 参数、手抄模型 ID | 盘点已有 CLI 与订阅，勾选即用（沿用 setup.md 的探测先行、申报兜底） |

## 形态

布局沿用三栏：**左栏资源设置，中栏控制台消息流，右栏方案与编排**。主线是接入资源 → 在控制台单线聊天或应用模式 → 收结果裁决。对话图保留为派发后的次级视图。

**定案（09-13）：对话即图**。推翻 08-30「对话与结果是末端」和「中栏是一条线性聊天」。参照 PiX（`D:\work\agentteam\COMPETITIVE-LANDSCAPE.md` 09-13 节）：会话不是一条线，是一张从左向右生长的图，分叉是日常动作，不是事先规划。只取形态不取代码（无 license，且与 pi 会话格式绑死）。

- **节点 = 一轮**：一条用户消息 + 一个模型的回复与工具调用。节点上带厂商色点、模型 ID、档位、thinking、可见性、写权限。
- **分叉（fork）就是派发**：在任意节点上 `@agent/模型`，从这里长出一条新分支。分支的上下文 = 根到分叉点的路径，不用再配。同一节点 @ 三家 = 扇出比对。
- **扇入只有一种节点：验收**。它有多个父节点，收「用户原话 + 各父分支的产物」。PiX 是树，没有扇入；本产品要它，所以图是 DAG。
- **可见性 = 分叉点 + 剔除**。从材料节点分叉，上游只有材料，天然盲；从方案节点分叉，天然共享。节点属性里的「盲」保留，含义收窄为：分叉时把路径上的模型回复剔掉，只留用户消息和附件。
- **写权限跟分支走**：可写分支各自一个 worktree，只读分支不建。
- **预设是图章**：模式不再是装进阶段条的固定三段，而是在当前节点盖一个子图（出方案 → 三条执行分支 → 验收）。盖完每个节点都能单独改、能再分叉。
- **图是聊出来的，不是画出来的**：没有自由连线，节点只能从已有节点分叉，扇入只能是验收。编排动作只有两种：在节点上 @，或盖预设。

**上下文跟随分支的代价**：PiX 的分支是同一个 pi 会话的分叉，本产品的分支是不同厂商的 CLI 进程。切到另一家的分支，控制台把根到分叉点的路径序列化成 prompt 喂给新进程，有损（丢 thinking，见 landscape 对 pi 的论证）。只读验证者够用；可写分支靠 worktree 延续，不靠上下文延续。

**定案（08-30）**：保留 coffeecli 式的工作区（文件树）、会话记录、修改记录，按 tab 排，用户可开关；从头实现（路线 C），可读 coffeecli 源码学结构、不复制。任务列表做成默认关的 tab。

| 栏 | 内容 |
|---|---|
| **左：资源** | **只列可派发的模型**（已冒烟通过的），按 agent 分组，一级是 agent（壳）、二级是该 agent 下的模型。点模型即把 `@agent/模型` 插进输入框。不放状态胶囊、不放探测与手动输入按钮——那些是装机期的动作，频率与这栏不匹配。栏底一行汇总「N 个待冒烟 · M 个未接入 · 管理 →」，进接入页。不显示额度条。 |
| **中：控制台** | 主视图是用户消息、模型回复和系统提示组成的消息流。默认发给当前 agent，`@显示名` 只改派当前一条；应用模式后，对话图在后台建立，结果逐路回到消息流。对话图作为次级视图保留原有节点、分叉和结果检查能力。 |
| **右：方案与编排** | 上半：当前节点的子图预览（例：`fable-5 出方案 → [codex/terra ｜ kimi/k3 ｜ pi/glm-5.2] 盲审 → 验收`），节点可点开改模型 / 档位 / thinking / 可见性 / 写权限；「编辑编排」打开表单式构建器；预设是图章，「应用」= 在高亮节点上盖这个子图。不放说明面板（界面已满，用户定 08-30）；改为「讲解」入口，打开独立页面讲每个预设做什么。任务列表需求不大，做成可开关的 tab。 |

**接入页（定案 08-31）**：`接入资源` 从左栏搬到独立页面，顶栏齿轮或左栏底部链接进入，形态是 **agent 卡片网格**（借鉴 coffeecli 的 Workspace 选择界面）。一张卡 = 一个 agent：标记、名称、版本、检测状态、该 agent 下全部模型及各自状态（已接入 / 待冒烟 / 未接入），卡底放「探测 / 冒烟 / 手动输入」。冒烟通过的模型才进左栏。这样把**装机期的管理**与**每次派发的挑选**彻底分开——两者频率差一个量级，混在一栏是左栏显乱的根因。

派发目标永远是模型，agent 只是通道（壳 ≠ 模型）；资源按 agent 分级是为了接入和探测方便，路由与独立性仍按厂商算。

**通道架构定案（09-13）：pi 是所有非原生订阅模型的默认通道，cc-switch 降级为发现提示。** 依据是当日实测（skill `references/evidence.md`「pi 的固定足迹与宿主隔离实测」）：pi 无工具 405 token、只读工具 1.5k、`--system-prompt ""` 时 21，对比 claude -p 12k 起、codex 20k；`--no-context-files` 实测挡住用户级 `~/.pi/agent/AGENTS.md`，盲验隔离可标「完整」；三个 provider（DeepSeek 官方、qwen token plan、智谱 coding plan）共 31 个模型；密钥归 `pi auth` 管，控制台进程里不出现 key，密钥六铁律变成设计上不碰。落点：
- claude / codex / kimi 三个 CLI 只承接各自的 OAuth 订阅；其余模型一律经 pi。接入页读 `models-store.json` + `pi --list-models`，冒烟真发一次请求（`--list-models` 有 ≠ 有权限，qwen plan 下 deepseek-v4-flash 实测 403）。
- 盲审、仲裁、前提抽查默认走 pi `--no-tools --no-context-files`；真身核对比对事件里的 `responseModel`（zai 端点实测把 glm-4.7 静默换成 glm-5.3-flash）。
- TASK-01 的 cc-switch.db 读取降为「发现提示」（发现已配 provider 时建议加进 pi），不再作为派发通道；`cc_switch.py` 路径不进源码。
- 第 4 期：走 pi 的节点用 pi 会话文件续接（`--session-id`），上下文跟随分支对 pi 节点近似无损；跨 CLI 才走有损序列化。
- 风险如实记：pi 是第三方项目，模型清单会漂；开工具时它有自己的 agent 系统提示（约 1.2k）；landscape 记过的 issue 4187（SDK 方式打 GLM coding plan 端点的封号风险）在接入页标一句。

**各 agent 的探测事实源**（调查记录 `docs/proto/resources-research.md`，2026-08-30）：

| agent | 存在检测 | 模型清单 |
|---|---|---|
| Claude Code | `claude --version` | 官方型号，无本地清单 |
| Codex | `codex --version` | `~/.codex/models_cache.json` |
| Kimi Code CLI | `kimi --version` | `~/.kimi-code/config.toml` `[models]` |
| **pi** | `pi --version` | `~/.pi/agent/models-store.json`（provider → 模型数组，含 baseUrl / contextWindow）；`pi --list-models` 列已鉴权可用模型；`pi auth` 看 provider 就绪性。一个 provider 可挂多个模型，支持 OpenAI / Anthropic 兼容端点。用户已用它替代 cc-switch 接多个 coding plan |
| cc-switch | `cc_switch.py list` | cc-switch.db 映射（只读） |

借鉴 coffeecli：静态注册表（binary 名、分档）+ `where`/`which` 探测 + 用户覆写文件（`~/.coffee-cli/tools.json`）。Vibe Kanban 的两级是 executor → variant（运行参数预设），不是模型。

- 一个对话窗。`@厂商/模型` 把当前任务发给该模型的独立会话，回复回到对话窗。
- **轻量的含义**：不托管 agent 的终端，不做文件浏览器、编辑器、终端模拟。每个 @ 在底层是拉起官方 CLI 并延续会话。
- **一次性续聊定案（09-01）**：每轮起一个进程、靠会话 ID 接上下文，三家已实测全 PASS（08-30）。不走长驻协议——NyaTerm 的 Codex 通道走 `codex app-server` 常驻 JSON-RPC，那是为了聊天区的逐字增量；本产品 G2 只要一行文字状态，常驻带来的进程生命周期管理不值这个价。长驻与 ACP 一并放第 5 期。
- 可见性跟角色走，不是全局开关：
  - **@执行者**：默认拿到当前对话的上下文。一个 @ 就走，用户不做任何隔离操作。多数任务在这里。
  - **@验证者**：默认盲。控制台自动把原始材料放进空目录、注入 `AI_CROSS_PEER=1`、只读白名单、材料走 stdin，**并关掉宿主自己的用户级指令加载**。用户只点"盲审"。
  - **盲的边界（09-01 实测）**：空目录只挡住项目级文件。`claude -p` 即使 `--tools ""` 且 cwd 为空目录，仍会把用户级 `~/.claude/CLAUDE.md` 注入上下文（模型能原样复述其中的专有名词）；加 `--restricted` 才不注入，鉴权不受影响。`CLAUDE_CONFIG_DIR` 指向空目录会连凭据一起隔离掉（`Not logged in`），不能用。各通道的等价开关在 TASK-03 逐个测出来；测不出的，界面标「隔离：部分」，不按盲的算。
- agent 之间默认互不可见；信息在 agent 间流动只有两条路：用户手动转发，或预设定义的流水线传递。

## 视觉纪律

**定案（08-31）**：走开发者工具的通用视觉语汇——等宽字承担结构、中性灰底、单一强调色、发丝边框。参照对象是 ThinkRail（JetBrains InnovationHub，Apache-2.0）这类界面，取其做法，不取其布局与配色：它是三栏 IDE，中心动作是改文件；本产品的主线是接入资源 → 看到调用方案 → 手动编排。

| 条目 | 规定 |
|---|---|
| **字体分工** | 正文与标题用 IBM Plex Sans。结构性文字用 IBM Plex Mono：模型 ID、provider 与 agent 名、路径、命令、任务 ID、版本号、token 数与耗时；数字开 `tabular-nums`。中文状态词仍用 Sans——等宽字体对中文字形无效。 |
| **分块** | 用 1px 边框和背景差分块，不用阴影。阴影只留给浮层（下拉、弹窗、抽屉）。**边框只给真容器**（栏、消息气泡、弹窗、卡片区块）；列表行不做容器，只用 hover 背景差分。 |
| **圆角** | 容器一律 8px，列表行 4px，胶囊标签取全圆。色点等图形不受此限。 |
| **强调色** | 全局只有一个 `--accent`，用于主按钮和选中态。 |
| **状态胶囊** | 胶囊只给需要快速扫描的异常状态（待冒烟、运行中、失败）。常态与完成态用色点或纯文字——所有状态都做成胶囊，绿色就贬值，黄色警告会被淹没。 |
| **字号阶梯** | 六级：12 辅助 / 13 次要 / 14 正文 / 15 基准与栏目标题 / 16 弹窗标题 / 18 页标题。不许出现 0.5px 步进。 |
| **厂商色** | 七个厂商色只做小面积标识：色点、3px 左边线或顶边线、标签文字色。不做大面积填充，不做按钮底色。 |
| **间距** | 内边距与间隙取 4 的倍数。例外只有行内小标签，统一 `2px 8px`。 |
| **图标** | 统一线框，1.5px 描边，颜色随文字色，不用实心图标和多色图标。 |

理由：本产品满屏是模型名、档位、命令和数字，等宽字让它们天然对齐；厂商色是功能性标识（一眼看出这段是谁跑的），一旦大面积用就失去区分作用。

## 三个引擎、两个开关

模式可以多，底层机制只有三种。新模式 = 给某个引擎换一套预设，不是新功能。

| 引擎 | 机制 | 写盘 |
|---|---|---|
| **扇出比对** | 同一份输入 → N 个隔离实例 → 收回并排 | 只读 |
| **流水线** | 阶段串行，上下文往前传；一个阶段内可并行 | 单写者 |
| **分工合并** | 拆任务 → 各领一块（各自 worktree）→ 合并 | 多写者 |

共享对话（一个 thread 大家都看得见）是流水线的退化形式：所有节点同一阶段、互相可见。

每个节点两个开关：**可见性**（共享 / 盲 / 只收指定上游）、**写权限**（只读 / 单写者 / 自己的 worktree）。

## 经济模式

"强出方案、便宜执行、强验收"的拆分本身是对的。项目五轮基准：档位几乎不影响正确率，便宜执行者写代码和贵的一样准。便宜模型翻车只有两种情况，都与档位无关：深任务关了 thinking（便宜、快、自信、全错，零警告）；让模型亲自算而不是写代码。经济预设把这两条写死，这是它和"选个便宜模型"的区别。

预设内置：
1. **三个角色一次定**：出方案 / 执行 / 验收，每个角色选厂商 + 档位 + thinking，之后所有任务复用。
2. **旋钮规则写死**：执行者遇链式任务自动开 thinking；数值任务 prompt 强制"写代码并运行"；单步小任务不外派；同类小任务合并成一次调用；harness 通道自动收窄 `--tools`。
3. **每阶段用量**：只展示这次工作流用了哪些模型、各消耗多少 token、耗时。成本核算（美元、额度百分比）不是本产品的事，交给统计工具；且三家 CLI 目前都没有可编程的额度读取路径（见待验证 ④）。
4. **验收默认换厂商**：用户可为省额度改回同厂商，界面标"复核，非独立验证"。

如实说的边界：控制台能把贵模型用在刀刃上，压不下总用量的地板（每次 harness 调用约 12k 系统提示底座砍不掉）。宣传按"贵模型用在该用的地方"说，不按"省钱"说。

## 自定义工作流

用户要能快速指定自己的编排，例如：Fable 5 出方案 → gpt-5.6、kimi-2.7、deepseek-v4-flash 三者并行执行 → glm-5.3 验收。

**数据模型**：预设 = 阶段列表；阶段 = 一个或多个节点（同阶段并行）；节点 = 模型 + 档位 + thinking + 可见性 + 写权限。盖到对话图上时展开为子图：阶段间串行 = 父子关系，同阶段并行 = 同一父节点分叉，末段若是验收 = 扇入。上一阶段全部完成后才进入下一阶段。展开后就是普通节点，可单独改、可再分叉（09-13）。

**一行记法**（内部表示，也是高级用户的输入方式）：

```
fable-5 → [gpt-5.6 | kimi-2.7 | deepseek-v4-flash] → glm-5.3
```

节点属性用后缀：`glm-5.3@blind`（盲）、`kimi-2.7#high`（thinking 高）、`deepseek-v4-flash:rw`（可写）。省略即取角色默认值。

3. **红绿核对门**（中，引擎）。修正轮交回来的测试，把修复回退再跑一次，红了才算数——这是审查员没有 shell 时唯一能证明「测试不是同义反复」的办法。引擎已有派发前快照（`before_dir`），可做：修正轮结果 → 回退到快照跑验证命令（期望失败）→ 恢复再跑（期望通过）→ 两次都对才进结果屏，否则标「测试未钉住」。对应 Runbook 第 6 条。
4. **额度用尽识别 + 自动切备选**（中）。今天 Claude 子代理撞会话额度、昨天 kimi 撞 5 小时窗口，都是人工改派。通道层把 429 / 403 / 「session limit」/ 「resets at」这类响应识别成「额度用尽」（区别于真失败），有备选（`Target.fallback`）就自动切并在结果卡注明「主 X 额度用尽，已切备 Y」，没有备选就把重置时间写进节点，不算失败。资源页给该模型标「额度用尽至 HH:MM」。对应用户 09-14 的「限额即换家」。

6. **控制台 tab 的在飞任务条**（小）。用户 09-15 指出：主控只派不做，用户随时能和它说话而不打断任务。控制台要让这一点可见——控制台 tab 顶部一条细状态条：在飞几路、哪家、跑了多久、有没有卡住（复用心跳与空转判定），点开跳到对话图。这也是「控制台 + 看板」闭环里看板的最小形态。
7. **模型备注与用途标签**（小，资源页）。实现者之间的差异要记住（修正轮用 sol，luna 敷衍过；kimi 5 小时窗口；GLM haiku 档审查要 15–25 分钟）。资源页每个模型给一行备注 + 用途标签（实现 / 修正 / 审查 / 拆分），预设的角色默认模型按标签取。对应 Runbook 第 2 条。

不做成功能的：任务书写法、heredoc 的坑、窗口真跑清单——这些是编排者的手艺，写在 Runbook 里就够。

## 派发的触发方式（09-16 定案，用户提出）

用户问的是全产品最难的一个点：日常就在控制台里正常聊天，什么时候该把活派出去？让模型自己判断（skill 现在的做法）实测不稳定——模型要一边干活一边记住元规则，漏触发和误触发都常见。让用户每次先选模式又违背「不用记」。

**定案：建议 + 一键裁决。不自动执行，也不要求用户先选。** 这就是产品第一天定的「模型提议、用户裁决、控制台执行」，只是把它落到派发的触发上。

- **默认没有模式。** 打开就是控制台的单线聊天。经济模式只是「真要派发时的默认预设」，不是聊天前的前置选择。
- **三个入口，同一条建议条**：
  1. 控制台（装了 ai-cross skill）觉得该派 → 调 `aicross propose`，只登记建议、不执行；
  2. 用户在控制台输入框点「建议派发」或按快捷键；
  3. 用户在控制台里打 `/派发`（可带模式，如 `/派发 盲审`）。
- **建议条一行**：普通区域显示`建议派发 · 经济模式 · 3 路 · 回车采纳 · Esc 忽略 · Tab 换模式`；终端有焦点时显示`Ctrl+Enter 采纳 · 或点右侧按钮`；其它输入控件有焦点时只显示`点右侧按钮`。模式名、「采纳」与「忽略」均可点击；采纳才真发。
- **永不自动执行。** 失败代价不对称：漏判只是少一次并行核对，误判要花额度、可能改文件，而且是静默的。做成建议后，漏触发的代价是零，误触发的代价是一个 Esc——模型判断不稳这件事从「会乱花钱」降级成「多一行提示」。
- **要不要出建议条用现成判据**：`isSmallEconomyTask`（<120 字、无附件、不含「测试 / 验证 / 实现」这类词）命中就不出。设置里已有的「归类模型」做可选的第二判据，默认关——多一次模型调用换一个同样不稳的判断，不划算。
- **主动换模式**：建议条上 Tab，或 `/派发 盲审`。右栏预设下拉退回编排图的工具，不再是主入口。

配套：预设下拉去掉「基础模式 / 自定义模式」组头（三行加一个标题反而碎），只保留「更多模式」的折叠。

## 控制台就是对话窗（09-16 定案，用户裁决）

**用户原话要点**：只保留一个控制台进行操作交互；不要默认启动 Codex；编排必须能在当前对话中直接使用。

### 为什么要改

产品此前有两个互不相通的世界：

- **原生 CLI 会话**（控制台 tab）：好用，但只能跟一家说话。用户在 codex 的原生界面里打 `@kimi`，命中的是 codex 自己的文件搜索，回「no matches」——他以为这里能 @ 别家模型，因为产品的主张就是这个。
- **对话图**：能派多家，但右栏「应用」在没有选中节点时是禁用的。从会话那个 tab 看过去，编排永远是死的，用户当然「没搞懂怎么用」。

`AGENTS.md` 写的产品定义是「用户在一个对话窗里 @ 各家模型，模型提议、用户裁决、控制台执行」。借 coffee 形态做壳之后，实现漂成了「在 tab 里托管各家原生 TUI」，与定义背离。这次把它扳回来。

### 定案

**旧称统一改为「控制台」。控制台不再是一个托管原生 TUI 的壳，它就是对话窗本身。**

1. **只有一种主 tab**：控制台。「系统终端」与「对话图」从新建菜单撤掉，降为控制台内的次级视图。
2. **中栏是我们自己的消息流**，不是别人的 TUI。用户直接打字：
   - 默认**单线**，发给当前选定的那一家，靠各家的续聊能力连续对话（已实测：`codex exec resume`、`claude -p --resume`、`pi --session-id`、kimi ACP）。
   - `@<家名>` 把这一条改派给那一家。
   - `/派发` 或建议条回车 → 多路，走既有引擎。
3. **永不替用户起会话**：新 tab 先让用户选 agent 与目录。上次的选择作为**预选项**填好、回车即用，但不自动按下。（原「有可用默认就直接起」的 09-15 定案作废——实测是每开一个 tab 就无声起一个 codex。）
4. **编排对当前控制台生效**，不再要求「先开图、再选节点」。选模式点应用，就把当前这句话按该模式派出去，图在后台自动建。
5. **对话图降为「看这次派发」的视图**，不是用户要先打开的东西。
6. **原生 TUI 保留，它是「agent 窗口」**（09-16 用户补充：「coffee 的原生 TUI 就是 agent 窗口，我们可以保留就好了」）。它不再是「你聊天的地方」，而是**某一家 agent 自己的窗口**：
   - 从控制台里的一次派发能直接打开对应那一路的 agent 窗口，看它自己的界面、用它自己的 `/model`、回它自己的审批弹窗。
   - 从接入页/左栏点某个模型也能开一个它的 agent 窗口。
   - 它**不在「新建 tab」菜单里**——新建只有控制台一种。agent 窗口是「为某个 agent 打开」，不是「新建一种 tab」。

### 代价（写清楚，别到时候当意外）

这是目前为止最大的一期，但比最初估的小一档：**原生 TUI 不扔**，所以 `/model`、权限审批、各家自己的快捷键都还在，只是挪进了 agent 窗口，不在你打字的那个地方。真正要新写的是控制台的消息流与单线续聊。分期做，先出能用的一步。

### 09-18 补：控制台里的 `/` 命令、技能与权限（经 ACP）

用户实测反馈：控制台里用不了 `/技能` 和各家原生命令，调 MCP 被拒。原因是单线聊天用一次性 CLI（`claude -p --tools Read,Grep,Glob`、`codex exec -s read-only`），没有交互界面。

- **单线聊天改走 ACP**：claude（`claude-agent-acp`）、codex（`codex-acp`）、kimi（`kimi acp`）。流水线节点不变，claude / codex 仍用一次性 CLI（盲审要无工具）。ACP 起不来自动回退一次性 CLI。
- **`/` 补全**：各家会话建立时推来的命令清单（技能、`/compact`、`/review` 等），按 agent × 目录缓存。
- **权限卡片**：读类放行；写文件类照旧拒绝（控制台聊天不改文件）；执行命令与 MCP 调用在消息流里弹卡片，只有「允许一次 / 拒绝」，永不持久授权；盲节点永不弹。关掉 tab 时挂着的卡片按拒绝回。
- **拿不到的**：`/permissions`、`/resume`、`/help` 这类只有交互窗口才有的命令，ACP 不报。前者由卡片替代，续聊由控制台自己管。
- 这比 agent 窗口（第 6 条）更贴合「控制台就是对话窗」：大部分原生能力不用离开控制台。agent 窗口留作兜底。

### 09-21 补：`@` 别家时补上它没看到的对话

各家各有自己的续聊会话，`@kimi` 发出去的原本只有当前这一句，kimi 不知道此前用户与别家聊了什么。现在发给某一家时，控制台把**它上一条回复之后、别人说过的那一段**拼在当前消息前面。做法参照 Ekko Studio 群聊的历史投影（`D:\work\agentteam\COMPETITIVE-LANDSCAPE.md` 09-21 节）；它每轮重建全量历史，本产品各家有原生续聊，只补增量。

- **补什么**：用户消息（剥掉开头的 `@显示名`）与成功的模型回复，标记沿用对话图的 `[用户]` / `[模型回复 agent/model]`，末尾 `[当前消息]`。系统提示、失败或超时的回复、发给某一家的 `/` 原生命令不补。
- **补多少**：续聊只补增量；新会话、会话失效重开、引擎内部回退一次性 CLI 时补全量。单条 4000 字符留头尾，合计 24000 字符从最早的丢。
- **认会话**：回复上记 `resumeKey`（agent + provider + model 的派发目标）。只在成功、没走备选、回了会话 id、且不是 `/` 命令的那一轮记。不按回复上显示的模型名认——那是引擎报回的真实型号或占位文字，与派发目标常不相等。
- **看得见**：消息流里一行「已附带此前 N 条对话给 X」；用户那条仍显示原文；实际发出的全文在留痕里。
- **不影响**：模式派发与盲节点不带控制台历史，盲的仍然盲。
- **Later**：模式派发的共享节点要不要带控制台历史；超长时用摘要代替丢弃。

## Cursor Projects 的外部印证与可借项（09-16，待用户裁决）

### 形态被外部印证了，不改设计

Cursor 2026-09-10 发布的 Projects（beta）是：一条长期线程、只跟一个**协调智能体**说话，它「不自己写代码，只指挥别的 agent」，子 agent 并行跑、可以点开任一个实时看过程。这与我们 09-15 定的「总指挥只派不做」、09-16 定的「控制台就是对话窗」几乎是同一结论。**这是印证，不是要改什么。**

不重合的三处正是我们的立足点，写下来是为了以后别被「人家也有」带偏：

1. **跨厂商**：Cursor 的模型全在它自家计费里转，没有「验收换一家」「盲审」这类默认值，验证交给用户审 PR。我们的核心是给没有 verifier 的任务外接一个**错误相关性更低**的 verifier。
2. **资源**：Cursor 烧它自己的 token；我们调用户**已有的各家订阅 CLI**。
3. **裁决**：Cursor 的协调者自主派发，人在 PR 处把关；我们是派发前、收结果时**两道闸门**，建议条回车采纳才发（09-16 定案）。

### 待裁决：共享上下文文件

Cursor 的 Project 带一组文件，在它用到的所有机器间同步，agent 把调研、对代码库的认识、用户偏好写回去，后续 agent 复用。

我们现在的等价物是**手写**的：`tasks/README.md` 的 Runbook、资源页的模型备注（第 4 期第 7 条）、`.dispatch/` 留痕。可以考虑让执行者把「怎么测这个服务」「这个项目的坑」一类经验写回工作区的一组文件，之后派发自动带上。

这句话把产品的验收标准说清楚了：**aicross 做成什么样算对，看它像不像我们开发它时用的这条会话。** 不是像 Cursor，是像这条会话——因为这条会话已经连续跑了四天、交付了三十多个任务，是被证明过的工作方式。

### 这条会话里协调者实际做的事，与产品现状的差距

| 协调者实际会做 | 产品现在有没有 |
|---|---|
| 写**任务书**：契约只追加、禁区文件、验证命令、换行规则、「不 commit 不 push」 | **没有**。派发只有一句话 + 一个模式，没有可携带的约束 |
| 一个工作树一个写者，按文件重叠排期 | 蜂群有（第 3 期），但不覆盖普通派发 |
| **不信报告，自己重跑**四件套 | 有红绿核对，但没有「编排者独立复跑」这一步 |
| 两家跨厂商盲审，材料只给原文 | 预设里有盲审模式，口径一致 |
| 合成修正轮清单，标出两家共同/各自独有 | **没有**。结果卡是并列呈现，不做合成 |
| **验伪审查结论**：09-16 两家审查的头号问题都是错的，清单开头要写「不要改这条」 | **没有**。没有地方记「这条我核过，是错的」 |
| 只做一轮修正，剩余进 backlog | 修正轮上限有（TASK-12），backlog 这个去处没有 |
| 合并后再跑一遍验证，然后**在窗口里人肉过一遍** | **没有**「最后人肉验收」的位置 |

### 结论（不改现有排期，作为后续的取舍依据）

差距集中在**两头**，中间的执行环节已经够用了：

- **派发前**缺「任务书」这个物件——今天多次靠它防住实现者跑偏（禁区文件、不许删原生 TUI、不许在 Rust 里重写 resume）。产品里对应的应该是比「一句话 + 模式」更厚的一层，但**不能厚到要用户填表**；建议条（09-16 定案）是它的雏形。
- **收结果后**缺「编排者核实」与「留下判断」——审查会说错话（09-16 实例：Gemini 说引擎不回传 session id、GLM 说备选会话 id 会污染续聊槽，两条都被代码与既有测试证伪）。产品若把多家意见直接摆给用户，用户会被错误意见带走。至少要能记住「这条被核过是错的」。

这两条都**待裁决**，不进当前排期。写在这里是为了以后判断「该不该加某个功能」时有个尺子：**它让这条会话的工作方式更容易被复刻，就值得；只是让界面更热闹，就不值得。**

## 借 Omnigent 的三条（09-30 用户定：采纳，未排期）

事实与对比见 `D:\work\agentteam\COMPETITIVE-LANDSCAPE.md`「2026-09-30 · Omnigent」一节。它的示例编排者 Polly 已跑通「多家 CLI 分写 + 换厂商审查」，与经济模式、盲审模式的机制大面积重合；差异在它由模型自主派发、不查模型真身、Windows 降级。以下三条只借做法，不改形态。

1. **agent 级就绪状态分出原因**。接入页现在对原生 agent 只探「CLI 在不在、登录了没」（「资源冒烟口径」一节）。细分为四态：**可用 / 未安装 / 未登录 / 版本过低**，每态在卡片上配一句下一步（装哪个包、跑哪条登录命令、最低版本是多少）。「版本过低」的最低版本按功能记：走 ACP 的 agent 以其 ACP 适配器能起的版本为准。模型级的「未验证 / 已验证 / 验证失败」三态不动；agent 不可用时，其下模型不进派发下拉，也不触发首次冒烟。

   - `ACCEPT.md`：这次派发的验收条件——验证命令、禁区文件、「契约只追加」这类约束。审查者对照它判「有没有做到」，不只对照用户原话猜意图。它来自派发前的约束，不含执行者的方案与推理，盲的边界不变。派发时没写约束就不生成，不造空文件。

   这一条也是「产品要复刻……」一节里「派发前缺任务书」的最小落点：约束先作为验收材料出现，再考虑让它更厚。
3. **节点标题按任务命名，模型退到次要位置**。现在 `nodeLabel`（`src-ui/src/graph/label.ts`）全界面统一显示 `agent/model`，同一张图里三路盲审就是三个模型名，看不出各自在干什么。改为主标题「角色 · 任务」（如「盲审 · 登录重构」），`agent/model` 作次标题，厂商色点照旧承担「谁跑的」。任务名依次取：蜂群清单条目的 `title`、图标题；都没有才退回 `agent/model`。材料与遗留节点不变。

## 定案（09-30）：对话留在宿主，aicross 只做引擎和结果查看器

**用户原话要点**：在 coffee 基础上做完，自己都觉得晕，不如直接用 skill 好用，看着乱。

**为什么改**：coffee 是终端工作区，中心是 tab、终端和文件树；本产品要的是「一个对话窗 + 派发 + 收结果裁决」。叠在一起后界面层数过多（控制台、agent 窗口、对话图、右栏编排、左栏资源、接入页、启动器、讲解页、文件树），与「不做」一节自相矛盾，积压里近六成是壳层问题。09-16 定的验收尺子是「像不像开发它时用的这条会话」，而这条会话就是宿主 + skill。CodePilot 的子 agent 呈现（对话里一行状态、点开看详情，见 `D:\work\agentteam\COMPETITIVE-LANDSCAPE.md` 09-30 节）说明多 agent 的可见界面可以小到这一档。

**机制**：
1. **说话的地方是宿主**。用户照常在 Claude Code、Codex、Kimi 等里工作，ai-cross skill 装在宿主里。aicross 不再提供对话窗、单线续聊与 `@` 改派。
2. **G1 在对话里**。skill 判断该派时给出一行建议（模式、几路、各派给谁），用户在对话里同意才发；「永不自动执行」（09-16）不变。
3. **引擎是命令行**。`aicross dispatch` 在不开窗口时也能跑完整条流水线：拉起各家 CLI、盲目录与隔离、只读护栏、真身核对、留痕 `.dispatch/`、验证门、修正轮、红绿核对、额度切备选、崩溃对账。`aicross status` 给每一路一行状态，skill 在对话里逐路报告。
4. **收尾回到对话**。全部结束后 skill 在对话里给汇总：共同结论、分歧、各自独有发现，附查看器入口。
5. **G3 在查看器**。一次 run 一页：各路并排、diff、验证输出、真身与用量，动作只有采纳 / 重派 / 放弃；采纳才提交（「diff 即事务，采纳即提交」不变）。
6. **资源接入是命令**。探测、冒烟、就绪状态由 `aicross resources` 输出，查看器里只读展示。

**保留**（规则与代码都沿用）：派发引擎与各家通道、盲审材料与隔离分级、真身核对、留痕契约 `aicross-dispatch/1`、流水线默认值（TASK-12/13/14）、蜂群合并、资源探测与冒烟。「借 Omnigent 的三条」仍然有效：第 1 条落在 `aicross resources` 的输出，第 2 条不变，第 3 条落在状态行与查看器标题。

**不再做**：控制台对话窗与单线续聊（含 ACP 单线、`@` 补对话）、agent 窗口与终端 tab、启动器、文件树、对话图的编辑与分叉操作、预设图章与右栏编排、表单式构建器、左栏资源与接入页、讲解页、界面缩放。对话图的数据结构作为引擎内部表示保留，不再是用户要操作的界面。

**待验证（动手前）**：
1. 流水线推进目前在前端 TypeScript（stamp → G1 → 流水线 → 结果落图，09-15 定案），`aicross dispatch` 也要求窗口在跑。无窗口运行要么把推进逻辑挪进 Rust，要么让这段 TypeScript 脱离窗口运行。先划清 `src-ui/src/graph/dispatch.ts` 与 `src/dispatch.rs` 的边界再选。
   **09-30 查清的边界**：
   - **Rust 一侧已能无窗口跑**：单阶段执行 `dispatch_stage_core(request, app: Option<AppHandle>)` 传 `None` 即可，窗口只用来收进度事件，现有测试就是这样调的。图、预设、角色的读写也在 Rust（`src/orchestration.rs`，含 `Graph` / `GraphNode` / `Reply` / `Target` 类型）。
   - **只在前端的是「一次派发怎么走完」**：`console-channel.ts` 的 `runConsoleDispatch` 做派发前检查（在飞上限、目标未接入 / 验证失败 / 额度用尽、项目目录不干净），盖预设（`stamp.ts`），拼每个节点的上下文与提示词（`context.ts`、`buildNodeRequest`，提示词模板在 `fixtures/prompts/`），再用 `runStageLoop` 逐阶段调 Rust、写回结果、推进修正轮与验证重试（`nextStageStep`、`reducePipelineStep`、`applyDispatchResults`）。这些函数都是纯逻辑，所有读写经注入的 `commands`（即 Tauri 调 Rust）。涉及 `graph/` 下 dispatch / context / stamp / validate / swarm / types / mutate 约 3000 行，其中一部分是界面辅助；对应测试约 2900 行。
   - **绑死在窗口上的状态有两处**：派发设置存在浏览器 `localStorage`（`dispatch-settings.ts`）；在飞 run 清单只在窗口进程内存里（`console_api.rs` 的 `RUNS`），所以命令行在窗口没开时直接报「控制台未运行」。
   **建议：推进逻辑挪进 Rust，命令行成为唯一引擎**（待用户裁决）。理由：执行、存储、类型已经在 Rust，缺的只是中间这层编排；挪完是一个二进制，不给用户加 Node 依赖，也不留两种语言各管一半。现有 TypeScript 测试当作规格逐条改写成 Rust 测试，行为以它为准。另一条路是把这段 TypeScript 打包成 Node 脚本、Rust 另开一个单阶段子命令给它调，起步快一些，但长期是两种语言、两个进程、进度要另走一条通道。两条路都要做的：设置从 `localStorage` 挪到文件（`~/.aicross/`），在飞 run 的状态落盘（`.dispatch/` 旁加 run 摘要），`aicross dispatch` 起一个后台进程后立即返回 run id，`status` / `wait` 读盘。
2. skill 在各宿主里能否「派出去 → 逐路报状态 → 结束后汇总」：Claude Code、Codex、kimi 的后台命令与等待方式不同，逐个实测。
3. 查看器用现有 Tauri 窗口砍到一页，还是本地网页。倾向前者以复用结果屏代码；技术选型排在 1、2 之后。
