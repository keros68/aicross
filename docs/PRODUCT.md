## 一句话

多厂商 agent 的派发控制台：用户在一个对话窗里 @ 各家模型干活，模型提议、用户裁决、控制台执行。它把 ai-cross 的规则从"提示词里的纪律"变成"界面上的默认值"。

## 解决什么

| 痛点 | 现状 | 本产品 |
|---|---|---|
| 性价比：想"强模型出方案、便宜模型执行、强模型验收" | 在 Claude Code / Codex 里手工配子 agent 上手难；自动挡（ultra 类）既不省也不快 | 一次定角色，之后每个任务复用；经济预设内置拧对旋钮的规则（见「经济模式」） |
| 准确度 | 同厂商复查失败模式相关 | 验收默认换厂商；盲审是一等公民 |
| 可控 | 模型既提议又执行，用户只能看 | 派发前、收结果时两道闸门，不点不发 |
| 上手 | 写 agents/*.md、记 CLI 参数、手抄模型 ID | 盘点已有 CLI 与订阅，勾选即用（沿用 setup.md 的探测先行、申报兜底） |

## 形态

布局照 coffeecli 的三栏：**左栏资源设置，中栏对话，右栏方案与编排**。主线是接入资源 → 看到调用方案 → 手动编排，对话与结果是末端。

**定案（08-30）**：保留 coffeecli 式的工作区（文件树）、会话记录、修改记录，按 tab 排，用户可开关；从头实现（路线 C），可读 coffeecli 源码学结构、不复制。任务列表做成默认关的 tab。

| 栏 | 内容 |
|---|---|
| **左：资源** | 两级。一级是 **agent**（壳）：Claude Code、Codex、Kimi Code CLI、pi、cc-switch 桥、手动添加。二级是该 agent 下的模型资源（pi 下面是它接的各家 coding plan）。每级支持**自动探测**（读该 agent 的本地事实源：codex `models_cache.json`、kimi `config.toml`、pi 的模型清单、cc-switch 映射）和**手动输入**（模型 ID、档位、备注）。条目带状态（已接入 / 待冒烟 / 未接入）、来源、最近冒烟日期。接入流程沿用 setup.md：探测先行、申报兜底、冒烟后入清单。不显示额度条。 |
| **中：对话** | 正常聊天区，用户自己打 `@agent/模型`（只列已接入的）。**默认共享上下文**：@ 出去的 agent 拿到全部对话，派发前不弹材料勾选；只有盲审等隔离类预设才把模型回复默认排除（用户定，08-30）。中栏只留一行"当前方案"提示。 |
| **右：方案与编排** | 上半：当前方案的阶段条（例：`fable-5 出方案 → [codex/terra ｜ kimi/k3 ｜ pi/glm-5.2] 盲审 → 验收`），节点可点开改模型 / 档位 / thinking / 可见性；「编辑编排」打开表单式构建器；预设只是往阶段条里装一套方案。不放说明面板（界面已满，用户定 08-30）；改为「讲解」入口，打开独立页面讲每个预设做什么。任务列表需求不大，做成可开关的 tab。 |

派发目标永远是模型，agent 只是通道（壳 ≠ 模型）；资源按 agent 分级是为了接入和探测方便，路由与独立性仍按厂商算。

**各 agent 的探测事实源**（调查记录 `docs/proto/resources-research.md`，2026-08-30）：

| agent | 存在检测 | 模型清单 |
|---|---|---|
| Claude Code | `claude --version` | 官方型号，无本地清单 |
| Codex | `codex --version` | `~/.codex/models_cache.json` |
| Kimi Code CLI | `kimi --version` | `~/.kimi-code/config.toml` `[models]` |
| **pi** | `pi --version` | `~/.pi/agent/models-store.json`（provider → 模型数组，含 baseUrl / contextWindow）；`pi --list-models` 列已鉴权可用模型；`pi auth` 看 provider 就绪性。一个 provider 可挂多个模型，支持 OpenAI / Anthropic 兼容端点。用户已用它替代 cc-switch 接多个 coding plan |
| cc-switch | `cc_switch.py list` | cc-switch.db 映射（只读） |

借鉴 coffeecli：静态注册表（binary 名、分档）+ `where`/`which` 探测 + 用户覆写文件（`~/.coffee-cli/tools.json`）。Vibe Kanban 的两级是 executor → variant（运行参数预设），不是模型。

- 一个对话窗。`@厂商/模型` 把当前任务发给该模型的独立会话，回复回到对话窗。
- **轻量的含义**：不托管 agent 的终端，不做文件浏览器、编辑器、终端模拟。每个 @ 在底层是拉起官方 CLI 并延续会话（依赖各 CLI 的 resume 能力，见「待验证」）。
- 可见性跟角色走，不是全局开关：
  - **@执行者**：默认拿到当前对话的上下文。一个 @ 就走，用户不做任何隔离操作。多数任务在这里。
  - **@验证者**：默认盲。控制台自动把原始材料放进空目录、注入 `AI_CROSS_PEER=1`、只读白名单、材料走 stdin。用户只点"盲审"。
- agent 之间默认互不可见；信息在 agent 间流动只有两条路：用户手动转发，或预设定义的流水线传递。

## 三个引擎、两个开关

模式可以多，底层机制只有三种。新模式 = 给某个引擎换一套预设，不是新功能。

| 引擎 | 机制 | 写盘 |
|---|---|---|
| **扇出比对** | 同一份输入 → N 个隔离实例 → 收回并排 | 只读 |
| **流水线** | 阶段串行，上下文往前传；一个阶段内可并行 | 单写者 |
| **分工合并** | 拆任务 → 各领一块（各自 worktree）→ 合并 | 多写者 |

共享对话（一个 thread 大家都看得见）是流水线的退化形式：所有节点同一阶段、互相可见。

每个节点两个开关：**可见性**（共享 / 盲 / 只收指定上游）、**写权限**（只读 / 单写者 / 自己的 worktree）。

## 经济模式

"强出方案、便宜执行、强验收"的拆分本身是对的。项目五轮基准：档位几乎不影响正确率，便宜执行者写代码和贵的一样准。便宜模型翻车只有两种情况，都与档位无关：深任务关了 thinking（便宜、快、自信、全错，零警告）；让模型亲自算而不是写代码。经济预设把这两条写死，这是它和"选个便宜模型"的区别。

预设内置：
1. **三个角色一次定**：出方案 / 执行 / 验收，每个角色选厂商 + 档位 + thinking，之后所有任务复用。
2. **旋钮规则写死**：执行者遇链式任务自动开 thinking；数值任务 prompt 强制"写代码并运行"；单步小任务不外派；同类小任务合并成一次调用；harness 通道自动收窄 `--tools`。
3. **每阶段用量**：只展示这次工作流用了哪些模型、各消耗多少 token、耗时。成本核算（美元、额度百分比）不是本产品的事，交给统计工具；且三家 CLI 目前都没有可编程的额度读取路径（见待验证 ④）。
4. **验收默认换厂商**：用户可为省额度改回同厂商，界面标"复核，非独立验证"。

如实说的边界：控制台能把贵模型用在刀刃上，压不下总用量的地板（每次 harness 调用约 12k 系统提示底座砍不掉）。宣传按"贵模型用在该用的地方"说，不按"省钱"说。

## 自定义工作流

用户要能快速指定自己的编排，例如：Fable 5 出方案 → gpt-5.6、kimi-2.7、deepseek-v4-flash 三者并行执行 → glm-5.3 验收。

**数据模型**：工作流 = 阶段列表；阶段 = 一个或多个节点（同阶段并行）；节点 = 模型 + 档位 + thinking + 可见性 + 写权限。阶段之间顺序执行，上一阶段全部完成后进入下一阶段。

**一行记法**（内部表示，也是高级用户的输入方式）：

```
fable-5 → [gpt-5.6 | kimi-2.7 | deepseek-v4-flash] → glm-5.3
```

节点属性用后缀：`glm-5.3@blind`（盲）、`kimi-2.7#high`（thinking 高）、`deepseek-v4-flash:rw`（可写）。省略即取角色默认值。

**表单式构建器**（主要入口）：阶段按行排列，每行"添加节点"，同一行的节点并行；每个节点点开选厂商/模型（从 manifest 读，不手抄）、档位、thinking、可见性。构建器与一行记法双向同步。保存为预设后出现在模式清单里。

拖拽画布是同一数据模型的另一种视图，后置：工作流深度通常只有 3–4 段，画布的收益小于维护成本，先看表单够不够用。

**扇入节点收什么**（默认，可改）：验收节点收「用户原话 + 上游产物」，不收上游的推理与方案文本；盲审节点只收原始材料。这是 ai-cross 框架隔离在工作流里的落点。

**并行节点之间**默认互不可见，各自的输出并排交给下一阶段。

## 与 ai-cross skill 的关系

- skill 留作模型侧：在宿主会话里产出路由提案和 prompt，规则文件是共同的事实源。
- 控制台是执行侧：接管 `cc_switch.py` 那层（拉起 CLI、注入环境变量、只读白名单、stdin 送材料、留痕）。
- 契约是文件：`manifest.md`（通道 × 档位，带来源列）、`.dispatch/*.md`（需加机器可读 frontmatter：通道/模型/档位/thinking/角色/状态/token/耗时）、`STATE.md`。

## 不做

- 不托管终端、不做编辑器和文件浏览器。
- 不做通用 agent 框架、不定义新协议。
- 不复用第三方对订阅 OAuth 的封装；只拉起官方 CLI 进程。
- 不做 G2 的实时动画。
